# 头程缓存与同步：客户端对接要求

本文件是待服务端确认的契约建议，不代表服务端已实现。本轮仅调整采集看板前端，未修改、访问或部署服务端实现。

## 已实现的客户端行为

- 默认近三个月，支持近一个月、近七天、自定义日期。日期按北京时间，首尾日期包含在内；近三个月按日历月回退并处理月底。
- 日期用于真实平台查询窗口，不使用对齐时间代替订单/平台业务日期过滤。
- 页面读取和“刷新服务器缓存”只调用现有 GET 缓存接口，不发起平台抓取。
- “真实抓取缺失头程”针对当前搜索及列筛选下的所有结果（不限当前页），只提交尚无有效金额的 XM，0 金额视为有效。所有 XM 均有金额时不自动转为全量刷新。
- 每页25/50/100条；筛选重置页码；导出包含全部筛选结果及同步详情。当前为客户端分页，尚不是数据库分页。
- 未返回同步记录时显示“同步记录未提供”，不推断无数据或未发货。

## 待服务端确认：现有接口扩展

GET `/api/freight/quotes` 继续返回 `quotes` 数组，并建议增加：

```json
{
  "quotes": [],
  "updated_at": "2026-11-12T05:15:00+08:00",
  "capabilities": { "date_range_query": true },
  "sync_records": {
    "XM示例": {
      "state": "partial",
      "attempt_count": 2,
      "last_synced_at": "2026-11-12T05:15:00+08:00"
    }
  }
}
```

`updated_at` 是服务器缓存实际更新时刻，不能用本次GET响应时间代替。前端另外显示本次读取时间。`sync_records` 为XM键控对象。金额记录及同步记录必须覆盖相同缓存快照，失败不能清除已有有效报价。

只有服务端实际支持日期、缺失补抓并验证参数后，才声明 `date_range_query: true`。未声明时，新前端不发送真实查询，提示先接入接口，防止旧接口静默忽略日期。

POST `/api/freight/{platform}/query` 建议接受：

```json
{
  "xms": ["XM示例"],
  "date_from": "2026-08-12",
  "date_to": "2026-11-12",
  "timezone": "Asia/Shanghai",
  "missing_only": true
}
```

必须把日期实际应用到各平台查询控件或接口，而非仅接收字段；不支持的平台应明确返回错误。服务器再次去重并排除已有有效头程金额的XM，避免排队期间重复抓取。响应为已受理任务，不代表查到金额；最终结果由缓存和同步记录返回。

## 待服务端确认：同步语义

| state | 展示 | 判定依据 |
| --- | --- | --- |
| never | 尚未同步 | 明确存在记录但从未尝试 |
| found | 已获取头程 | 有有效金额，包括0 |
| all_not_found | 所有平台均无结果 | 本轮所有应查平台账号都成功完成指定日期范围查询，均无结果 |
| not_shipped | 未发货，暂无头程 | 可信订单状态或平台业务证据；不得由无结果次数推断 |
| partial | 平台查询未完成 | 有平台未查、未登录、跳过或覆盖范围不完整 |
| failed | 查询失败 | 采集异常；与成功查询但无结果分开 |

`attempt_count` 是每XM实际开始的同步轮次数，不是页面点击次数、GET次数或各账号次数相加。单次轮次横跨多个平台只计一次；纯忙碌跳过不计。需要服务端统一轮次标识/去重，避免前端逐账号提交计重。`last_synced_at` 为该XM最近一轮完成时刻，不能用对齐时间代替。

服务端还需保存逐平台账号的结果、查询窗口、尝试次数、开始/完成时间、错误原因、未发货证据、最后成功时间与有效覆盖范围。上述汇总状态必须从这些证据计算。平台账号集合变化后，旧的全平台无结果不能直接代表新集合也无结果。建议后续接口提供详情与分页历史，目前前端仅消费汇总字段。

## 待服务端确认：全局缓存和凌晨更新

1. 初始化：全局拉取每个已绑定平台账号近三个月全部数据，逐页遍历并持久化，不受当前用户选择、页面筛选或已有XM列表限制。保留平台/账号及业务单据标识，避免多账号覆盖丢失或金额重复相加。失败的平台不应标记初始化完成。
2. 日常：服务器每天北京时间04:00启动一次任务，在04:00–06:00窗口执行。补抓近三个月仍无有效头程的XM；已有金额不重复抓取。无需客户端保持打开。
3. 明确区分初始化的全量扫描与日常的缺失补抓；如需每天刷新全量平台数据，应由服务端确认额外负载和触发策略，不能把缺失补抓宣称为每日全量。
4. 防止多实例重复调度，与手动任务互斥/去重；失败持久化并按受控规则下次重试。未发货记录不能永久排除，发货后需再次进入补抓。
5. 提供最近任务状态、最近成功时间、下次计划时间、平台覆盖和缓存范围。过期、失败、停机错过窗口需可见，不能显示为成功。
6. 缓存读取必须只查数据库，不能在GET内部隐式访问平台。服务器负责权限隔离。

## 后续数据库分页建议（尚未接入）

数据量增大后，建议新增统一对齐缓存查询接口，支持页码/页大小、搜索、店铺/订单/头程状态/物流筛选和稳定排序；返回 `rows`、`total`、`page`、`page_size`、`updated_at`。日期过滤需明确使用平台哪种业务时间，缺日期数据不得静默消失。服务端确认接口前，当前客户端保持现有全量GET并在本地分页；不要让旧接口返回截断数据却不通知客户端。

## 联调验收

- 用平台网站放宽到近三个月后可查到的同一XM验证日期确实生效。
- 初始化分页完整，全局结果不随前端搜索变化；次日只补抓缺失XM。
- 反复切页、筛选、刷新缓存不触发真实平台请求。
- 任一平台未登录/失败时不得显示所有平台无结果；未发货状态必须可追溯证据。
- 跨账号一轮只计一次；0金额不重抓；同步时间及读取时间清楚区分。
- 服务端新增契约、调度和部署均待服务端团队落实，本轮未上线这些能力。
