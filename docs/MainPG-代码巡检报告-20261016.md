## 二、P0 问题详情

### P0-1　`/api/customer/me` 返回 500 而非 401（活跃中）

**根因**：`<服务器>/wh-workbench/MainPG/local-runtime/wh_local/customer/auth_server.py:1174`

```python
@app.get("/api/customer/me")
def me(authorization: str | None = Header(default=None)) -> dict[str, Any]:
    token = _bearer_token(authorization)
    account = _account_by_token(db_path, token)   # ← 这里会抛 SessionRevokedError
    if account is None:
        raise HTTPException(status_code=401, detail="invalid bearer token")
    return {"ok": True, "account": account}
```

同文件 `_required_account()`（3351 行起）是**正确写法**，它有：

```python
try:
    account = _account_by_token(database_path, token)
except SessionRevokedError:
    raise HTTPException(status_code=401, detail="session revoked, ...")
```

而 `/me` 路由绕过了 `_required_account`，直接调 `_account_by_token`。

**触发条件**：会话被撤销时（他端登录顶替 / 主动登出 / 改密）——`_account_by_token` 在 3326 行 `raise SessionRevokedError()`。

**实测影响**：
- 24h 内 36 次 `GET /api/customer/me → 500`，最近一次 06:13 UTC（约 40 分钟前），**仍在发生**
- 客户端每 3 分钟轮询一次 `/me`（日志规律：03:26:37 → 03:29:37 → 03:32:37 …）
- 因为拿到的是 500（服务端错误）而非 401，前端无法识别为"会话被顶替"，**进入永久 500 循环**，用户卡在坏掉的登录态
- 涉及 IP：121.225.69.253、222.94.140.187、61.176.79.147

**同类风险排查结果**：全文只有 3 处直接调 `_account_by_token`——
| 位置 | 路由 | 是否安全 |
|---|---|---|
| 1174 | `GET /api/customer/me` | ❌ **漏保护** |
| 2898 | `POST /api/customer/invitations/generate` | ⚠️ 有 `except Exception → _raise_http_error`，但见下方说明 |
| 2944 | `GET /api/customer/invitations` | ⚠️ 同上 |

注意 `_raise_http_error`（5170 行）**不映射 `SessionRevokedError`**，末尾是 `raise exc` 原样抛出 → 这两处同样会 500。只是它们是管理员专用、流量极低。

**建议修法**（未执行）：把 `/me` 改为 `account = _required_account(db_path, authorization)`，或在 `_raise_http_error` 里补 `SessionRevokedError → 401` 分支。

### P0-2　`batch/settle` 409 风暴：24 小时 9859 次

**实测数据**（customer-auth，24h）：

| 状态码 | 次数 | 占比 |
|---|---|---|
| 200 | 15901 | 61.5% |
| **409** | **9857** | **38.1%** |
| 401 | 90 | 0.35% |
| 500 | 36 | 0.14% |
| 403 | 23 | — |

`9859 / 9859` 全部来自 `POST /api/customer/billing/batch/settle`。

**服务端行为是正确的**，不是 bug——`auth_server.py` → `billing.py:3852`：

```python
if str(freeze["status"]) != "frozen":
    # 冻结已被 TTL 清扫释放（status='released'）或其他非 frozen 终态时，
    # 继续结算会把 locked_points 扣成负数触发 CHECK 约束（500）。
    # 明确拒绝（409），客户端应停止重试。
    raise HTTPException(status_code=409, detail="batch freeze is no longer active")
```

即：批次过了 **AI 预留 TTL 6h** 被清扫释放后，客户端的结算请求必然 409。

**根因在客户端**：老客户端收到 409 后只打失败标记、**保留 open 记录**，导致每次收尾/对账都重打一轮必然失败的请求 → 永久重试。

**好消息：修复已完整存在于本地仓**，不是半成品（我一开始误判，已复核）：
- `local-runtime/wh_local/modules/product_processing/batch_billing.py:114` `abandon_freeze()` —— 置 `settled=True` 停止重试，写 void 留痕，不删记录
- `local-runtime/wh_local/modules/product_processing/service.py:6217`（任务收尾）与 `:6286`（对账）两处 `except CustomerAuthRejected` → 调用 `_abandon_batch_freeze`

**所以这不是待写代码，是待发布**。按 `MEMORY` 记录，该修复（`3826ee120` + `6bb1085f2`）已推 origin，等在下一个客户端版本里出去。
