## 0. 一条最重要的经验

`token_info` 返回的 `apiScopeList`（本店 78 个）**是应用登记范围，不等于 client 能调**。
判断能不能调，必须真打一次、看返回：
- `CLIENT_PERMISSION_DENIED` → 没开通
- `3000000 xxx 不能为空` / `2000030 ...` → **通了**，只是参数不对

## 4. 与文档对照的结论（goods.add payload）

2026-10-28 用真实 `_draft()` 逐字段比对文档 `bg.glo.goods.add` 样例：

- **顶层 25 个字段全覆盖**；未发的 5 个（`productOuterPackageImageReqs`、`goodsLayerDecorationReqs`、`sizeTemplateIds`、`showSizeTemplateIds`、`productCustomReq`）都是**有条件才发**（有外包装图 / 有详情图 / 填了尺码表 / 填了商品标签）。
- **SKC**：文档有 `colorImageUrl`，我们已发（取轮播首图或变种预览图）。
- **SKU**：文档有 `thumbUrl`，我们已发（变种预览图，留空回退 SKC 图）。
- 我们额外发了 `materialImgUrl`、`personalizationSwitch`、`productSecondHandReq`，是实测需要 / 语义支持的可选字段，文档样例未列。
- `mainProductSkuSpecReqs` 我们发的是全零占位对象 —— 文档示例是真规格，但实测「1 SKC + N SKU」时全零是唯一能通过的形态（真实规格会报 `Duplicated`），**保持现状**。

## 5. 接下来如果要推进，需要先解决的事

1. **改库存** → 让服务商开 `bg.btg.goods.stock.quantity.get/update`。
2. **说明书上传** → 让服务商给一份**真实可用的请求样例**（现在 12 种写法都被判文件为空，怀疑网关要 multipart 或另有字段）。
3. **尺码表** → 上架服装类目后，用真实类目拉一次非空 `sizeSpecDataList`，确认结构再做前端选择器。
4. **尺寸图检测** → 需要一个真实的 `mallId`（`bg.mall.info.get` 被拒），且检测耗时较长，需确认多久出结论。

## 6. 与「真实成功案例」的差异（2026-09-27 发布成功，productId 9282408501）

拿到 `Temu发布接口完整请求参数.md`（一次真实成功调用）后逐字段比对，差异与处理：

| 案例里有、我们没发 | 处理 |
|---|---|
| `productSkuMultiPackReq`（`numberOfPiecesNew: 12`，多件装） | **已补**：SKU 加 `pieces_per_pack`，>1 时按案例结构发；1 不发。界面「包装信息 → 每件装数量」 |
| 顶层 / SKC / SKU 的 `width` / `height`（800×800） | **故意不发**：这三个是图片尺寸类字段，我们曾因硬编码 800 触发 `2000306 详情图宽度不正确`；现在尺寸按实际测量走，宁可不发 |
| SKC `isBasePlate: 0` | 不发（默认 0，底板是定制类专用） |
| `productSkuBarCodeReqs: []` | 不发（空数组无意义） |
| `productCustomReq: {cat10Id: 0, isRecommendedTag: false}` | 我们发的是 `{goodsLabelName}`（填了才发），两者可选，不冲突 |

| 取值差异 | 说明 |
|---|---|
| `shipmentLimitSecond`：案例 **777600（90 天）** | 我们原默认 1 天（等于承诺 24 小时发货，POD 做不到）→ **已改默认 7 天**；本机存档和批量模板里的旧 1 天也会被纠正；需要更长可自行改大 |
| `mainProductSkuSpecReqs`：案例也是**全零占位** `{specId:0,...}` | 印证我们「1 SKC + N SKU 用全零」的做法是对的，别改成真规格（会报 `Duplicated`） |
| `productSkuSpecReqs`：案例用的是 `spec.create` 自建值（「4件」） | 我们仍只用类目预设值（自建值会报「不合法的规格属性」），保持现状 |
| 详情图：案例 20 组 | 我们不限数量，按上传张数发 |

结论：案例里唯一**真正缺**的可用字段是多件装，已补；其余都是可选或明确不该发。

## 7. 发布链路细节自检（2026-10-28，共 5 轮）

以两次真实成功案例（productId 9282408501 / 45629654961）为唯一准绳，把组装出的
payload 递归 diff 一遍、再把前端每个解析/换算函数过一遍。

### 7.1 已修

| 问题 | 后果 | 修法 |
|---|---|---|
| `productPropertyReqs` 多带 `numberInputValue` / `valueGroupId` / `valueGroupName` 三个空字段 | 真实案例里没有这三个字段，空值一起发可能被判「属性不合法」 | 只在真有值时发（空值一律不发），与案例字段集完全对齐 |
| 数值型属性（vid=0，靠 `propValue`/`numberInputValue` 传文本）被必填校验判成「vid 不在可选值内」 | 类目里只要有数值属性（长度/容量之类），这个类目永远发不出去 | vid≤0 时改校验「至少填了文本」，不做 vid 白名单 |
| 换店/新增店/删店后不重取运费模板与发货仓库 | 表单里留着上一家店的 `freightTemplateId` / `warehouseId`，提交必被拒或建到别的仓 | 加 `reloadShopScopedData()`，三个入口都调，并重置表单与每行变种的仓库 |
| 尺码表按类目缓存，换店不刷新 | 新店的尺码表设置看不到 | 尺码表 effect 加 `shopEpoch` 依赖 |
| 发布成功后看不到商品 id（只有「网络中断反查」那条路径显示） | 只能去翻原始 JSON 才知道建出来的是哪件 | 前端 `goodsIdOf()` 与后端台账同一套字段顺序，成功提示直接带 id |
| 类目明确不需要尺码表时仍带旧 `sizeTemplateIds` | 字段已隐藏、用户改不掉，带上去只会换来一句莫名报错 | `sizeChart.has === false` 时发空数组 |
| 批量发布路径与单条不一致：货号不清洗、详情图不带尺寸、规格每条草稿都 `createSpec`、warnings 被丢弃、不显示 id | 批量发 20 条会建 20 套重复规格；详情图必踩 2000306 | 货号用同一套 `safeCode`；详情图统一走 `uploadDetailImage(800)` 拿真实宽高；规格先用类目预设值（匹不到且类目无预设值才自建，且一次批量只解析一次）；完成文案带 warnings 与商品 id |

### 7.2 复查结论（无需改）

- 顶层 23 个字段与真实案例**完全一致**（除案例那件商品没详情图，故我们多发 `goodsLayerDecorationReqs`）。
- 换算：重量 g→mg、尺寸 cm→mm、申报价元→分，与案例数值口径一致。
- `mainProductSkuSpecReqs` 全零占位、`productSkuSpecReqs` 只发 4 键、`vid=0`：与案例一致，保持。
- 切店时后端 `_reset_client()` 会清服务层读缓存，`_client_key` 变化会重建客户端 → 不会串店（前端才是缺口，已补）。
- `goods.add` 强制 `max_attempts=1`；台账 pending 30 分钟自动失效，不会被一次崩溃挡 24 小时。
- 失败重试不会重复上架：网络错误会先 `find_published_goods` 反查。

### 7.3 仍存在的限制（不是 bug，但要知道）

- `siteSupplierPrices` / `productI18nReqs` / `freightTemplateId` 都是**单站点**形态。以后要发 EU 多国站，得按 `bindSiteIds` 逐个站点补价格与多语言标题。
- 中文标题只会给 warning，不会生成英文标题；批量路径的标题来自草稿，也不翻译。
- `productOuterPackageImageReqs` 的字段结构（`[{imageUrl}]`）没有真实成功案例背书，首次用到要盯回执。

## 8. 「桌布」这类无销售属性类目的支持（2026-10-28 第二轮自检）

截图暴露的问题：类目 `10498`（家居/厨房用品/厨房和餐厅/餐厨布艺/桌布）在 Temu **一个销售属性
都没有**（`attrs.get` 实测 17 个属性，`isSale` 全为 false），而发布链路强制要求颜色+尺码规格
（`main_specs` / `specs` 都是 `min_length=1`，前端 `ensureSpec` 必须匹到类目预设值）。

→ 结果：这类类目**在界面上能选能填，点发布必然抛「不是该 颜色的合法值」**，永远发不出去。
界面原先只有一句「只能按单 SKU 发布」的提示，但代码里没有这条路。

### 修法

| 层 | 改动 |
|---|---|
| 后端 schema | `SkcInput.main_specs` / `SkuInput.specs` 允许空数组（单 SKU 商品） |
| 后端 service | `sale_pids` 非空（类目确实有销售属性）却一个规格都没填 → 明确报错；属性表没有销售属性 → 规格声明与 SKU 规格都发空数组，`mainProductSkuSpecReqs` 仍保留全零占位 |
| 发布页 | `saleValueIndex.size === 0` 判定单 SKU：跳过 `ensureSpec`，只取第 1 行，多行时给 warning |
| 变种面板 | 新增 `singleSku` 开关：收起变种生成区，隐藏颜色/尺码两列（CSS `.is-variant-row.is-single` 改列宽） |
| 批量发布 | 同样按 `saleIndex.size === 0` 走单 SKU，不再对每个颜色/尺码 `createSpec` |

真实数据验证（只组装不提交）：`productSpecPropertyReqs: []`、`mainProductSkuSpecReqs` 全零、
`productSkuSpecReqs: []`、9 个属性齐全、联动把「木材类型/木种/面料类型」正确过滤。

### 顺带修掉的细节

- **「下拉 + 数值」属性填不了数值**：`封面材质` 这类属性既有 14 个预设值、又有单位 `%`
  （`numberInputTitle=成分比例`），原先只渲染下拉 → 比例永远填不进去 → Temu 回「请输入数值」。
  现在同时渲染下拉与数值框，`numberInputValue` 能正常带上；带单位的必填属性缺数值会被前后端一起拦下。
- 数值属性输入框的 placeholder 优先用 Temu 给的 `numberInputTitle`（如「成分比例（%）」）。
- 店铺账号（readOnly）与经营站点（disabled）加了灰底样式，避免看着像能改却改不动。
- 「存为预设」（仅分类+运费+仓库）与「存为产品模板」（含属性/尺码表/开关，批量发布要用）
  的 placeholder 与 tooltip 说清区别。

### 还没验证的

单 SKU 商品的 payload 结构（空 `productSkuSpecReqs`）**没有真实成功案例背书**：两次成功案例
都是有销售属性的商品。首次用桌布类目发布时要盯回执，若 Temu 要求别的写法（比如主规格也省略），
按第 6 节的表格补记。

## 10. 草稿库重构：服务端分页 + 按发布 payload 呈现信息（2026-10-28）

### 10.1 加载问题

原来 `GET /draft-library` 一次返回 80 条，前端切 50/页 —— 首屏要同时拉 50 张缩略图
（每张走鉴权 blob），滚动和翻页都在等图。

- **后端**：拆成 `collect_all_draft_entries()`（聚合，贵）+ `paginate_draft_library()`（切片）。
  聚合结果按账号缓存 60 秒，`page / page_size / source / q` 都只在缓存上切，翻页不重扫任务和批次。
  `source` 与 `q` 下沉到后端，`counts` 保持全量（筛选按钮上的数字不跟着筛选变）。
- **前端**：30 条/页，翻页真的只请求这一页；页签/关键字变化回第 1 页；
  搜索 300ms 防抖；翻页时保留上一页并压暗，不再闪成「加载中」；
  翻页/换页签/改关键字都清空勾选（避免跨页残留勾选导致「以为发 30 条、实际发 60 条」）。

### 10.2 信息呈现（照成功样例与实测清单）

列的先后顺序就是「能不能发」的判断顺序：

| 列 | 呈现什么 | 依据 |
|---|---|---|
| 产品 | 标题 + AI/POD 徽章 + 变体数 + 备注 | — |
| Temu 类目 | 完整路径（发布页选过的优先 → 草稿自带 → 红字「发布页选类目」）+ 美国站 | 类目是 `goods.add` 的第一前置；没选叶子类目发不出去 |
| 货号 | SKU 货号，未填标红 | `extCode` 必填 |
| 申报价 | `¥150.00` + `15000 分` + 「推算」标记 | 发布页填的是分，避免再乘 100 时算错；推算价来自导出表规则（成本×4，下限 ¥150） |
| 库存 | 数值；`0` 用橙色并注明「可建品但不可售」；未填是 `—` | 实测允许 0 库存，与「未填」必须区分 |
| 尺寸 · 重量 | `30×22×4 cm · 350 g`，缺项 `—` | `productSkuVolumeReq` / `productSkuWeightReq` 必填 |
| 完整度 | 绿「可发」/ 橙「缺 类目 / 申报价 / 重量 / 尺寸」 | 把 5 个硬性前置直接点名，不用进发布页才发现 |
| 更新 | 时间 | 排序依据 |

另外：顶部工具栏收成「页签 + 搜索框 + 批次说明 + 失败历史」一行；底部 30 条/页 + 越界页码自动夹回。

## 11. 草稿库显示「缺 货号 / 重量 / 尺寸」的根因（2026-10-28）

现象：POD 草稿在草稿库里货号空白、尺寸显示 `—×—×— cm · — g`、完整度提示「缺 货号/重量/尺寸」，
但这些数据 POD 导出表里明明都有。

根因：`pod_customization` 的**生成结果**（`pod_customization_batch_items` /
`pod_customization_style_grid_results`）里**没有 `skus` 字段**，而草稿库只读
`item["skus"][0]`，于是 `first_sku` 永远是 `{}`。真实数据在批次的
`listing_fields_json` 里：

| 字段 | 实际位置 | 说明 |
|---|---|---|
| 重量 | `listing_fields.skus[0].weight_g` | 与导出表第 15 列同源 |
| 申报价 | `listing_fields.skus[0].declared_price` | 第 9 列同源 |
| 长宽高 | `listing_fields.spec_card.cells` 的 `["SKU","Length","Width","Height"]` 行 | **单元格数值固定是厘米**，`display_unit` 只影响展示 |
| 货号 | `product_code_prefix` + style_index（导出表第 4 列「产品货号」） | 第 10 列那个「SKU 货号」常就是 `1`/`s`，跨批次会撞号 |

修法：`first_sku` 回退到 `listing_fields.skus[0]`；尺寸读规格卡原值（不做单位换算）；
货号优先用快照里显式存的 `sku_code`，否则用导出表同一套 `_product_code`（`POD-001`）。

> 顺带发现：`export.py::_sku_dimensions` 在 `display_unit="in"` 时会把厘米值换算成英寸
> 再写进**标着 cm 的列**（18cm → 7.09），导出表那一列的单位是错的。草稿库没走这个函数，
> 但导出表本身值得单独修一次。

### 11.1 第二轮：`listing_fields` 其实挂在**批次**上

上一轮只修了 `first_sku` 回退，POD 仍然显示「缺 重量/尺寸」，因为真正的坑更深一层：
`get_batch()` 返回的逐条 item（`batch_items` / `style_grid_results`）里**没有
`listing_fields` 这个键**，它在返回字典的**顶层**（`result["listing_fields"] = json.loads(batch["listing_fields_json"])`）。

- 之前：`listing = item.get("listing_fields")` → 永远是 `{}` → `skus` / `spec_card` / `category_name` 全空，
  价格只能退到下限 ¥150，货号/重量/尺寸一律显示「未填」。
- 现在：`listing = batch.get("listing_fields")`，items 里那份只作兜底；
  replica（爆款复刻）模式优先用 `replica_targets[style_index].listing_fields`（每款一份）。

真实数据验证（3 个批次 → 112 条）：货号 `POD-001..010`、重量 1g/100g、尺寸 18×10×8 cm、变体数 4，全部到位。

顺带把类目这一格改成三态，避免把「草稿自带分类」当成 Temu 类目：
`picked`（发布页选过，绿）/ `draft`（POD 模板自由文本，灰底写「草稿分类：xxx」）/ `none`（红字「发布页选类目」）。
完整度里只认 `picked` —— 自由文本不是类目 id，发布时照样得选。

## 13. 价格单位统一为「元」（2026-10-29）

界面上原来直接在变种表里让人填**分**（`1299` = ¥12.99），只靠右侧一行 `≈ ¥12.99` 提示。
填错一位就是 100 倍价差，而申报价是真正会扣钱的数。

### 结论：界面全用元，接口仍收分

| 层 | 单位 | 说明 |
|---|---|---|
| 草稿（POD / AI 导出） | 元 | `listing_fields.skus[].declared_price` 实测是 150 / 80 / 1.0 |
| 草稿库列表 | 元 | 不再附「15000 分」那一行 |
| 发布页输入框 | **元**（最多两位小数） | 表头 `申报价格(元)`、`建议售价(元)`、placeholder `12.99` |
| 组装 payload | 分 | 只在 `utils/price.ts::yuanToCents` 换算，`schemas.py` 的 `supplier_price: int` 不动 |
| Temu 接口 | 分 | `siteSupplierPrices[].supplierPrice` |

### 换算只有一处实现

新增 `web-frontend/src/modules/temu_publish/utils/price.ts`：

- `yuanToCents(value, label)`：正则 `^\d+(\.\d{1,2})?$`，**三位小数直接报错**而不是悄悄四舍五入
  （悄悄取整就是定价偏差）；空值/0 也拦
- `centsToYuanText(value)`：只给老数据迁移用，脏值原样返回，不生成假 `0.00`
- `formatYuan(text)`：展示用

发布页与批量发布都从这里引，不再各写一份。

### 老数据迁移（关键）

本机 `localStorage` 里存的变种行与变种模板，价格以前是**分**：

- `temu_publish_rows_v1:<account>`：`supplierPrice` / `suggestedPrice`
- `temu_publish_variant_templates:<account>`：`batch.supplierPrice` / `batch.suggestedPrice`

`migrateLegacyPriceUnit()` 在**读取 state 之前**把它们 ÷100，并写标记
`temu_publish_price_unit_yuan_v1`，之后永不再动。

> 为什么直接改存储而不是只改内存：React 严格模式会把 `useState` 初始化跑两遍，
> 只改内存的话第二遍又读到原始的分值，`1299` 就会变成 ¥1299。
> 直接在存储层改 + 写标记，两遍都读到已转换的值。

### 验证

换算前后**提交给 Temu 的分完全一致**（只是显示变了）：

| 草稿 | 旧（填分） | 新（填元） | 提交分 |
|---|---|---|---|
| ¥150 | `15000` | `150` | 15000 ✅ |
| ¥12.99 | `1299` | `12.99` | 1299 ✅ |
| ¥0.5 | `50` | `0.5` | 50 ✅ |

迁移：`"15000" → "150.00" → 15000`、`"1299" → "12.99" → 1299`、`"abc" → "abc"`（跳过）。

单测 `utils/price.test.ts` 4 条（真跑函数，不只是读源码）：整数/一位/两位小数、
浮点误差（12.29、3.35）、三位小数与脏值报错、迁移脏值保留、展示格式。

### 顺带

- 草稿价带入发布页前先 `moneyText()` 圆整到分：导出表按成本算出的 12.345 会被
  「最多两位小数」拦下，先圆整用户看到的和提交的一分不差
- 建议售价异常提示改成「两个都是元，不用换算」，不再提 ×100

## 16. `7000015 sign is invalid` 的根因：顶层空数组（2026-11-03）

### 现象

单 SKU 类目（如「桌布/亚麻布」10498，属性表里 `isSale` 全为 false）提交时，
网关一律回 `7000015 sign is invalid` —— 连业务校验都没到，看不到 Temu 到底要什么。

### 根因

网关**算签名时忽略空数组、转发时又把空数组带上**，两边算出来的 sign 对不上。
`catsmandatory.get` 长期报这个错（第 3 节）也是同一个原因：它的请求体里
`productPropertyReqs` 空时也被塞了 `[]`。

### 修法

顶层数组字段为空时**整个字段不发**，而不是发 `[]`：

| 位置 | 改动 |
|---|---|
| `service.py::build_goods_payload` | 返回前清掉为空的 `productSpecPropertyReqs` / `productPropertyReqs` |
| `client.py::mandatory_config` | 没有属性时请求体不带 `productPropertyReqs`（原来 `list(... or [])` 会塞 `[]`） |

不发之后，若 Temu 真要求这些字段，会明确回 `Cannot Be Empty`，比一句「签名无效」好定位得多。

### 预期效果

错误会从 `7000015 sign is invalid` 变成 `3000000 Product Specification Attribute Cannot Be Empty`
—— 说明请求终于走到业务校验了。**但单 SKU 类目仍然发不出去**：Temu 不接受
「类目没有销售属性 → 规格留空」这种发法，全零占位也不行，会继续要 `Reference Property Name` /
`Base Property Value`。这条路的结论是：**任何类目都必须给一个真实规格**。

### 深层空数组（未动）

单 SKU 场景 payload 里还剩 3 处空数组：

- `productSkuReqs[0].productSkuSpecReqs`（SKU 规格，Temu 报的 `Product SKU specification list cannot be empty` 就是它）
- `productSkuWhExtAttrReq.productSkuSensitiveAttrReq.sensitiveList` / `sensitiveTypes`

这些是**嵌套**字段，不参与顶层签名；而且 `productSkuSpecReqs` 空了在业务上本来就不合法，
删掉只会换个报错。先保留，若仍出现 7000015 再逐个收。

### 验证

- 真实桌布类目 10498 组装：顶层 22 个字段，**零空数组** ✅，属性联动照常过滤（封面材质/木材类型/木种/面料类型）
- 单测：96 passed（+3：顶层空数组不发、非空规格照发、catsmandatory 空属性不带该字段）

### 16.1 实测验证（2026-11-03，真实凭证，只读）

改完后直接调 `catsmandatory.get`（校验接口，不建商品），**签名单确实消失了**：

| 请求体 | 改前 | 改后 |
|---|---|---|
| 无属性（原来发 `[]`） | `7000015 sign is invalid` | `Does not currently support querying other category configurations` |
| 带一个属性 | `7000015 sign is invalid` | 同上 |

结论两层：

1. **空数组假设成立**——`7000015` 确实是空数组引起的，不发就没有了
2. **但这个接口还有第二个坑**：它只支持部分类目，桌布类目 10498 明确回「不支持查询其它类目配置」

所以 `check_mandatory` 的 `source` 仍然是 `attrs.get（网关不支持 catsmandatory，已回退）`，
这是对的——本地 `attrs.required` 才是可靠依据，网关那份只当补充。

### 16.2 goods.add 决定性验证（2026-11-03）

改完后直接打真实网关 `bg.glo.goods.add`，**故意把 `cat1Id` 改成 99999999**（不存在的类目），
确保不可能建出商品，但签名计算照常走：

| | 改前 | 改后 |
|---|---|---|
| 返回 | `7000015 sign is invalid` | `Product Specification Attribute Cannot Be Empty; Preview image cannot be empty; Product SKU specification list cannot be empty;` |

**签名错误彻底消失，请求进到业务层了。** 这个验证方式可以复用：

```python
payload = svc.build_goods_payload(draft)["payload"]
payload["cat1Id"] = 99999999          # 必然被拒，不会建出商品
svc.client().add_goods(payload)        # 看回来的是签名错还是业务错
```

`Preview image cannot be empty` 是测试用了假的 `a.jpg` 导致的，真实发布用的是上传后的
kwcdn 地址，不会踩。

### 16.3 结论：只剩规格这一条

签名问题已经闭环。单 SKU 类目现在的阻塞只有规格：

```
Product Specification Attribute Cannot Be Empty
Product SKU specification list cannot be empty
```

即「类目没有销售属性 → 规格留空」这条路 Temu 不接受，全零占位也不行。要发这类商品只有两条路：
换到有销售属性的类目，或者给类目造一个真实规格（要 `spec.create` 写店铺数据，需先只读探查）。

### 16.4 实测：无销售属性类目可以用「虚拟规格」发出去（2026-11-03）

用「无效类目 `cat1Id=99999999`」做安全实验（必然被拒、不会建商品），逐级补齐规格字段看错误怎么变：

| 变体 | 返回 |
|---|---|
| A 现状（商品级 / SKU 级规格都空） | `Product Specification Attribute Cannot Be Empty` + `Product SKU specification list cannot be empty` |
| B 商品级补全零占位（名称空） | 变成 `Reference Property Name cannot be empty` + `Base Property Value Cannot Be Empty` |
| C SKU 级补全零占位 | **`Product SKU specification list cannot be empty` 消失** |
| D 两级都补全零占位（名称空） | 两个 `cannot be empty` 全消失，只剩上面那两个名字/值为空 |
| **E 两级占位 + `propName="款式"` `specName="默认"`** | 规格错误**全部消失**，只剩 `Preview image cannot be empty`（测试用假图） |
| **F E + 真实上传的 kwcdn 图** | 只剩 `参数错误：Failed to retrieve leaf category`（故意设的无效类目） |

**结论：给无销售属性的类目补一个「款式: 默认」的虚拟规格（所有 id 填 0，只填名称），
就能通过 Temu 的全部校验。** 图片换成真实上传的 kwcdn 地址后，唯一的错误是故意制造的无效类目。

关键点：
- 名字必须**非空**，但 `pid / refPid / templatePid / specId / parentSpecId` 可以是 **0**
- SKU 级 `productSkuSpecReqs` 也必须给一条（4 键：specId/specName/parentSpecId/parentSpecName）
- 商品级 `productSpecPropertyReqs` 一条，13 键（照抄成功样例结构，id 全 0）

> ⚠️ 这是「绕过类目的规格要求」，不是类目本身支持规格。风险：Temu 审核阶段可能判
> 「规格信息不实」。首次用这种方式发布的商品**必须人工去后台看一眼**，确认前台展示正常、

## 17. 「属性都填了还报缺少必填属性」的根因（2026-11-03）

现象：桌布类目（10498）把 13 个属性全填了，页面绿条写「属性已填 13 项，还差 0 项必填」，
右上角也是「可提交」，但点检查必填/提交仍红字报：

```
缺少必填属性：形状、编织类型、材料、材质类型、织造方式、平方克重（g/㎡）、制作工艺
```

### 根因：`valueUnit` 是 `[""]`，被当成「有单位」

拉 10498 的属性表看这几个字段：

| 属性 | valueUnit | numberInputTitle |
|---|---|---|
| 形状 / 编织类型 / 材料 / 材质类型 / 织造方式 / 平方克重 / 制作工艺 | `[""]` | None |
| 封面材质 | `["%"]` | 成分比例 |
| 厚度（mm） | `["mm"]` | None |

Temu 对**无单位**属性返回的是 `valueUnit: [""]` —— 数组长度是 1，但唯一元素是空串。

而前端校验写的是：

```ts
if (item.valueUnit?.length && !pick.text.trim()) return true;   // ❌ 长度是 1
```

→ 判定「这属性带单位，必须填数值」。

但界面渲染用的是另一个判断：

```ts
const unit = item.valueUnit?.[0] ?? "";   // → ""，界面不渲染数值框
```

**结果：不给你输入框，却要求你填数值。** 这 7 个属性永远填不完，商品永远发不出去。
（封面材质 `["%"]`、厚度 `["mm"]` 因为真的带单位、真有输入框，反而正常。）

### 修法

统一成「单位本身非空」：

| 位置 | 改法 |
|---|---|
| `data/attributeModel.ts::missingRequiredNames` | `const unit = String(item.valueUnit?.[0] ?? "").trim();` 再用 `if (unit && !pick.text.trim())` |
| `pages/TemuPublishPage.tsx` 的 `number_input_value` | 同样按 `valueUnit[0]` 非空判断，不再用 `.length` |

后端 `_property_payload` 本来就是正确写法（`str(units[0] or "").strip()`），不用改。

### 测试

`data/attributeModel.test.ts` 新增行为用例：
- `valueUnit: [""]` / `[]` / 无该字段 → 只选下拉**算填好**
- `valueUnit: ["mm"]` / `["%"]` → 只选下拉仍**算缺**（真带单位的不许放宽）

前端 656 passed，tsc 0。

现象（同日第二次踩到，和 §18 不是一回事）：

- 顶部横条 + 右侧「发布检查」同时红字「请求的内容不存在或已被删除」，**没有错误码、没有上游原话**

### 排查结论

1. 媒体文件是好的：`product_processing_media_assets` 4577 条里 4568 条 ready 全都有文件；
   这次草稿带进来的 4 张图是 COS 公网链接，`curl` 全是 200 —— 排除 §18 那条路径
2. 真正的原因在**属性**，不在图片：
   - 草稿库的属性是按「估填那一刻」的 pid/vid 存的（`attrPicksStore` 的 `DraftAttrPrefill`）

   - 但内部 `attrPicks` 里 `vid > 0` 就算「有值」→ `missingRequiredNames` 放行
   - 一路走到 `goods.add`，Temu 收到不存在的 pid/vid → 「请求的内容不存在或已被删除」
3. 这句话为什么连错误码都没了：
   - 后端 `_gateway_message()` 其实已经包成
     `Temu 拒绝了这次提交：<上游原话>（错误码 xxx）`
   - 前端 `client.ts::toUserMessage` 里 `/not found|does not exist/i` **排在「已是中文→原样返回」之前**，

     错误码和原话一起丢掉 —— 排查时完全两眼一抹黑

1. `data/attributeModel.ts::pruneStaleAttrPicks(picks, attributes)`
   铺草稿属性之前按当前属性表过一遍：pid 不存在、vid 不在 `values` 里、空值空文本 → 丢掉并返回名字。

2. `TemuPublishPage.tsx` 恢复草稿属性时先 prune，把丢掉的项数/名字显示在自动填提示条上：
   「N 项草稿属性在 Temu 那边已经失效（…），已清空 —— 这几项要重新选，否则提交会被拒」。
   这样从「点提交才知道失败」变成「一眼看到缺什么」。
3. `client.ts::toUserMessage`：中文原因优先，不让 `not found / does not exist` 覆盖后端已经写清的话。
4. `client.ts::httpBlob`：404 时把请求 path 附在文案后面
   （草稿图 / 素材 / 商品 / 路由写错四种情况的文案原本一模一样）。
5. 详情图读文件失败也走 `readLocalImage()` 给可操作提示（原来只有轮播图那条路径有）。

## 20. 「图片读不到」的真身：预览地址签名只活 2 小时（2026-11-03）

现象：

- 详情图/轮播图缩略图显示「…」，一直转；提交时报「请求的内容不存在或已被删除」
- 但**图明明还在**：`product_processing_media_assets` 里 status=ready，`managed_path` 指向的文件在磁盘上（实测 183477 字节完好）
- 用户反复强调「我没清理过」

### 根因

`media_asset_service._preview_url()`：

```python
expires = ((int(time.time()) // 3600) + 2) * 3600
```

即**当前整点 + 2 小时**。`media_asset_content()` 校验：

```python
if int(expires) < now or int(expires) > now + 3 * 3600:
    raise LookupError("media asset link expired")
```

草稿库/发布页表单把当时那个带签名的地址**当普通字符串存了下来**（localStorage `temu_publish_form_v2`、
`DraftAttrPrefill`、草稿 entry 的 `carousel_images`）。过几小时/几天再用：

- `expires` 早过期 → `LookupError` → 路由 404 → 前端映射成「请求的内容不存在或已被删除」
- 用户看到的「图还在」（缩略图有时能显示，是因为签名还没过期的那会儿刚加载过）
- 重传图只有 2 小时有效期，第二天照旧 —— 所以怎么折腾都复现

排查走过的弯路：报错里只露出地址**末尾 60 字符**，那正好是 `signature`（sha256 hex），
去库里搜那个 hash 当然搜不到，一度误判成「记录在、文件没了」。
**教训：报错要露地址开头，不要露尾巴。**

### 修法

1. **后端** `ProductProcessingService.media_asset_file()` / `MediaAssetService.media_asset_file()`
   —— 新增「不校验签名、只认登录态」的读取路径。
2. **后端** `GET /media-assets/{asset_id}/content` 参数改为可选：
   - 带 `expires` + `signature` → 原签名校验（`<img src>` 直连用，`<img>` 带不了 Authorization）
   - 不带签名 → 必须 Bearer 已登录，`workspace_id` 用地址里带的（资产按 workspace 分目录）
3. **前端** `client.ts::stripMediaSignature()`
   —— `httpBlob` 请求前把 `signature` / `expires` 剥掉（**保留 workspace_id**），
   因为 `httpBlob` 自带 `Authorization`。一处改动覆盖所有读本地媒体的地方。
4. **前端** `TemuImageStrip.isPublicHttp()` 排除 `127.0.0.1` / `localhost`
   —— 原来把本地绝对地址当公网丢给 `<img>`，既带不了 Authorization、又卡在过期签名上，缩略图永远出不来。
5. 缩略图加载失败显示「失效」而不是一直「…」（用户以为在加载，其实永远等不到）。

### 验证

- `GET .../content?workspace_id=xxx`（无签名）→ **401**（说明走到登录分支，参数不再必填）
- `GET .../content?...&expires=1793517726&signature=...`（过期签名）→ **404**（原行为保持）
- 资产 `5291f96e6d644c819c458d6334b080aa`：ready / 183477 bytes / 文件存在

### 遗留

- `_preview_url()` 的有效期仍是 2 小时。`<img src>` 直连的场景（其它模块）过 2 小时同样会失效，
  这次只修了 temu 发布链路走的 `httpBlob`。要彻底根治得让各处都用「asset_id + 会话鉴权」取图。
- 草稿 entry 里存的仍是带签名的地址。长期看应该只存 `asset_id`，读时现签。

## 22. 不同类目的变种属性完全不一样：不能写死「颜色 / 尺码」（2026-11-03）

用户反馈：「很多产品都不一样，把所有类型都搞好行不行」。

### 原来的问题

| 位置 | 写死的东西 | 后果 |
|---|---|---|
| `findParentSpec(items, "颜色", 0)` / `"尺码", 1` | 按中文名找父规格，找不到靠下标 | 手机壳的「型号」、收纳盒的「容量」全靠下标撞运气 |
| `SpecMismatch.field: "颜色" \| "尺码"` | 把中文当内部键 | 校验结果和界面文案一起被写死 |
| 变种区标签「变种属性值二（尺码，逗号分隔）」 | 文案写死 | 明明是「型号」，界面上写着「尺码」，用户照着填错列 |
| `composeDraft` 生成 SKC 时无条件 `ensureSpec(sizeParent, ...)` | 假定两列都存在 | **只有一列销售属性的类目直接抛「Temu 父规格列表为空，无法创建规格」** |

### 修法

1. `findParentSpec` 支持关键字**数组**；新增两组常见叫法：
   - `FIRST_SPEC_WORDS`：颜色 / 色 / 款式 / 花色 / 图案 / 型号 / 风格
   - `SECOND_SPEC_WORDS`：尺码 / 尺寸 / 规格 / 容量 / 长度 / 大小 / 重量 / 数量 / 样式 / 型号
2. `pickSpecPair(specs)`：挑两列时**排除已选的**，保证两列不是同一个属性
   （类目返回顺序不保证，[型号, 颜色] 时两列会同时落到「颜色」上）。
3. `SpecMismatch.field` 改为内部键 `"color" | "size"`，界面展示时才映射成真实父规格名。
4. 页面新增 `colorSpecName` / `sizeSpecName`（取自 `parentSpecName`），传给 `PublishSkuPanel`；
   变种区所有文案（标签、placeholder、红字、表格列提示）都用它。
5. `composeDraft`：`if (sizeParent)` 才要求第二列，只有一列销售属性的类目正常发单规格 SKU。
6. `PublishSkuPanel`：`sizeParentId > 0` 才渲染第二列。

### 原则

**一个类目的名字都不要硬编码**。列名、可选值、必填项全部来自
`parentspec.get` + `attrs.get` 的返回，代码只负责「按返回渲染 + 校验」。

### 验证

- 前端 `npm run verify`：全绿（含 tsc）
- 新增断言：两列不重复、单属性类目不崩、文案使用真实属性名

## 23. 6000002 反复出现的真因：清缓存一直在空转（2026-11-03）

### 现象

同一个类目（10498 桌布）连续 6 次提交全部回：

```
Temu 拒绝了这次提交：货品类目属性更新，请刷新页面后重新创建货品（错误码 6000002）
```

点「刷新类目树」、刷新页面、重选属性，全都没用。

### 排查证据

后端日志里 6 条 `error_code=6000002`，但**"类目属性已更新，清掉…缓存 N 条"这行一次都没出现** ——
说明 §21 加的清缓存分支根本没生效。

### 根因：实例级缓存 + 拿不到当前实例

`router._handle()` 是模块级闭包，只有 `service`（**未绑定 owner** 的实例）可用：

```python
dropped = service.client().invalidate_categories()   # 清的是"另一个 client"的空缓存
```

而真正处理请求的是 `_service(actor).client()` —— **不同实例，不同 `_cache` 字典**
（`self._cache` 是实例属性）。于是：

1. 清缓存清掉的是那个临时实例里**根本不存在**的条目（返回 0 条，甚至抛凭证缺失被吞）
2. 实际请求的 client 仍然命中 1 小时 TTL 的旧属性表
3. 重拉拿到同一份旧表 →「没发现差异」→ 用户以为这功能坏了

### 修法

类目树 / 类目匹配 / 属性表是 **Temu 全网统一**的（与店铺无关），把这三类缓存的存储
提升到**模块级共享**：

```python
_SHARED_CATALOG_CACHE / _SHARED_CATALOG_LOCK / _SHARED_CATALOG_PREFIXES = ("cats:", "cat-match:", "attrs:")
def clear_shared_catalog_cache() -> int: ...
```

- `_cache_get / _cache_put / _cache_drop` 按 key 前缀分流到共享或实例缓存
- `invalidate_categories()` 同时清共享 + 实例
- `router._handle()` 直接调 `clear_shared_catalog_cache()`，**不再碰 service**（绕开 owner 问题）

**绝不能共享**：`parent-specs` / `freight:` / `warehouse:` 是店铺级数据，共享会串店。

### 另一个事实：Temu 侧刷新属性是异步的

同类 ERP 的官方帮助写明：「更新属性会有延迟，可以点击更新属性后等几分钟再填写商品属性」。
所以清完缓存立刻重拉往往还是旧表 —— 前端提示因此改成
「已清缓存，Temu 侧通常要等 1-2 分钟，请稍后再点『刷新类目树』」，
不再让用户去换类目。

### 验证

- 后端 `tests/test_temu_publish.py`：**103 passed**
  - 新增 `test_shared_catalog_cache_is_cleared_across_client_instances`：
    A 实例写入 → B 实例读得到 → 任意位置清 → B 立即失效；
    同时锁定 `parent-specs` / `freight:` 仍然隔离（不串店）
  - `test_invalidate_categories_also_...` 补了前置清理（共享缓存是模块级，会跨用例泄漏）
- 前端 `npm test`：**677 passed**

## 24. 6000002 的最终定位：我们调的是 V1 接口，后台走的是 V2（2026-11-03）

这也解释了：
- 卖家后台手动能上架（走 V2）
- 店里 218 个历史商品是成功的（它们用的是当时的 V1 属性，还没变）
- 换成新类目 / 属性被改过的类目就必失败

### 处理

1. **找服务商（YL）开通 V2 接口**：`temu.local.product.attributes.get`、`temu.local.goods.v2.add`

2. 开通后需要把 `client.py` / `service.py` 的属性获取与发品链切到 V2 结构（payload 字段不同，是一次迁移）
3. 过渡期：优先用**历史上发过的类目**，这些类目的 V1 属性还没变，仍可提交

## 26. 6000002 的真正根因：无销售属性类目补的是「假规格」（2026-11-03 已实测跑通）

### 结论先放

`6000002 货品类目属性更新，请刷新页面后重新创建货品` **不是属性问题，是规格问题**。

没有销售属性的类目（桌布 10498 / 桌旗 10497 / 餐垫 10493 这一整片）以前补的是
id 全 0 的占位规格 `款式/默认`。它能让「规格不能为空」的校验通过，但 `goods.add`
会**一直**回 6000002。换成**真实规格**（`颜色/默认`，真实 specId=20832）后，
同一份属性表立刻发布成功。

### 决定性实验（都在真实店铺上跑的）

| 实验 | 结果 |
|---|---|
| 12 个必填属性**逐个单发**（每次只发 1 条） | **12 条全是 6000002** → 跟发哪个属性无关 |
| 完全不发属性 | `3000000 Product Attribute Cannot Be Empty` → 属性确实在校验 |
| 完全不发规格 | `3000000 Product Specification Attribute Cannot Be Empty` → 规格必须有 |
| 发假规格（id 全 0，款式/默认） | 6000002 |
| 发真规格（颜色 1001 / specId 3002 黑色） | **success: true** |
| 发真规格（颜色 1001 / specId 20832 默认） | **success: true** |
| 假发类目 31035（isSale=2，真实规格） | 不报 6000002（报了 specs 配对错，另一回事） |

一句话：**`isSale` 为空的类目，规格必须来自 `parentspec.get` 的真实 specId，不能造。**

### 排除掉的（都不是原因）

- `productCreateTime`：带上当前 13 位毫秒和不带，返回的属性表**完全一样**（templateId 152662、
  17 个属性、templatePid 集合逐项相同）→ 属性表不是旧的
- `supportedType`：0 / 1 结果相同；2 → `6000000 supportedType 入参非法`
- 缓存：早就改成模块级共享并清干净，重拉同一份表
- 类目链 / 轮播图数量 / SKU 预览图 / showCondition / 缺字段：每修一项错误码都往前推进过
- 属性字段格式：成功案例的 `productPropertyReqs` 也是只有
  `pid/vid/refPid/propName/propValue/valueUnit/templatePid` 7 个字段，和我们一致

### 修法（已改）

1. `client.ensure_default_spec()`：优先取 `parentspec.get` 里名字含「颜色」的父规格，
   调 `bg.glo.goods.spec.create` 建一个「默认」值，返回
   `{parentSpecId, parentSpecName, specId, specName}`；结果按店铺缓存 30 天。
   实测 `spec.create` 是**幂等**的（同名重复建返回同一个 specId=20832），不会堆垃圾。
2. `_assemble_payload(draft, warnings, catalog, fallback_spec)`：没有规格时用真实规格生成声明，
   `pid/refPid/templatePid` 由 `_spec_decl_payload` 按「类目属性里有没有这个 parentSpecId」决定，
   `vid` 固定 0（填了会被判「主销售属性不合法」）。
3. 兜底规格建不出来（断网）时仍退回占位规格，但告警里**明说「这样提交大概率被回 6000002」**，
   不再让人瞎试。
4. 前端：`PublishSkuPanel` 的单 SKU 提示改成「颜色：默认」；
   6000002 且属性表无差异时不再让用户「等 1-2 分钟再刷」，改为指向规格问题。

## 28. 服务商凭据改为「安装包不带 + 服务器下发 + 指纹轮换」（2026-11-04）

原先尝试过把凭据加密随包（`temu_gateway.enc`，AES-256-GCM）。评估后撤掉：

密钥固定写在 wh_local/secrets.py（_ENC_KEY_SEED）
