# 安卓伴侣 App · 第一阶段接口清单与技术方案

> 定位：**伴侣型**（PC 工作台的随身延伸，而非独立工作台）
> 技术栈：**Flutter（跨端）**
> 版本基线：`APP_VERSION = 1.5.2`
> 编写日期：2026-10-08

---

## 1. 目标与范围

### 1.1 第一阶段（Phase 1）功能范围

| # | 功能组 | 依赖通道 | 是否免 PC |
|---|--------|----------|-----------|
| 1 | 账号（登录 / 注册 / 找回密码 / 改密 / 改用户名 / 退出）+ **手机 ↔ PC 账号绑定** | 云端 | 是 |
| 2 | 积分充值（支付宝）+ 订单 / 流水 + **签到领积分** | 云端 | 是 |
| 3 | 消息中心 + 公告（**按绑定账号定向下发**，PC 与移动端双端提示） | 云端 | 是（受限，见 §4.4） |
| 4 | 任务看板 + 轻审核 | 局域网 | 否（需 PC 在线） |
| 5 | 分享采集（淘宝 / 1688 / 天猫转发或复制链接）+ **拍照上传（短期中转）** | 局域网 + 云端中转 | 采集否 / 拍照可弱依赖 |

> 说明：第 4、5 项本质是「把 PC 的采集/AI 能力用手机遥控 + 回传」。其中**分享采集**必须走局域网通道；**拍照上传**采用「云端短期中转」以支持 PC 离线时先拍后同步。
> Phase 1 按**通道**拆成两批交付：
> - **P1-A（免 PC，云端直连）**：功能组 1 / 2 / 3
> - **P1-B（协同，局域网 + 云端中转）**：功能组 4 / 5

### 1.2 非目标（明确排除）

- 不做移动端本地 AI 处理（产品处理、尺寸图、POD 定制仍在 PC 端）。
- 不做移动端独立钱包体系（积分/账本一律以云端为权威）。
- 不做分站密码下发（本地 `_public_station_application` 明确永不返回分站密码）。
- **照片不做长期存储**：云端仅作「短期中转」，同步到绑定账号后即删除（见 §4.5）。

### 1.3 本轮补充需求（相对首版新增）

| 编号 | 需求 | 关键约束 |
|------|------|----------|
| N1 | 手机端账号与 PC 端账号密码联动，手机账号能与 PC **相互绑定** | 复用同一云端账号体系，密码一套；绑定为"设备绑定关系"，双向可见 |
| N2 | 后台给指定用户发公告时，同时提示其绑定的 **PC 账号 + 移动端账号** | 定向公告按 `account_id` 下发，PC/移动端各自拉取（双端一致性） |
| N3 | 拍照上传与 PC「商品组合」联动，拍完直传并同步到电脑端 | **服务器仅短期存储**，同步到对应账号后**删除** |
| N4 | 签到领积分（体验版 / 基础版） | 复用 `plan-basic/claim` + `daily-extra/claim` |
| N5 | 在线充值 | 复用 `billing/topup-orders`（支付宝） |
| N6 | 后续可能接入广告视频，与积分联动 | 仅预留导航卡位与积分流水 `source_type` 扩展，Phase 1 不实现 |

## 2. 总体架构：双通道

```
┌──────────────┐
│  Android App │
└──────┬───────┘
       │
       ├──► 通道 A：云端直连（免 PC）
       │      https://workbench.haocoming.top/auth-api      （账号 / 计费 / 充值 / 订单 / 设备绑定）
       │      https://workbench.haocoming.top/publish-api   （公告 / 反馈回复，带 x-auth-token）
       │
       └──► 通道 B：局域网协同（需 PC 在线）
              http://<PC-LAN-IP>:8010                        （采集 / 任务看板 / 草稿池）
              WS /plugin/session/{id}                        （实时指令通道）

┌──────────────────────────────────────────────┐
│ PC 本地工作台（127.0.0.1:8010, FastAPI）      │
│  · /api/customer/*  ← 云端 customer-auth 代理 │
│  · /api/messages/*  ← 本地 SQLite 同步表      │
│  · 采集队列 / 插件会话 / 草稿池                │
└──────────────────────────────────────────────┘
```

**关键事实**：本地 `127.0.0.1:8010` 上的 `/api/customer/*` 并非独立实现，而是 `remote_client.CustomerAuthClient` 对云端 `{auth-api}/api/customer/*` 的**透明代理**（路径、请求体、响应体完全一致）。
因此 App **免 PC 时可直接把基址换成 `auth-api`，契约零改动**——这是 P1-A 能脱离 PC 的根本原因，也是 **N1「账号密码联动」天然成立**的原因（手机与 PC 登录的是同一套云端账号）。

### 2.1 账号绑定与设备联动模型（N1 / N2）

```
        ┌──────────────────────────────┐
        │   云端账号 account_id（唯一） │
        │   用户名 / 邮箱 / 密码（一套）│
        └───────────┬──────────────────┘
                    │
        ┌───────────┴────────────┐
        │                        │
   [PC 端会话]              [移动端会话]
   device: pc_xxx           device: mobile_yyy
        │                        │
        └──── 设备绑定关系表 ─────┘
             binding: {account_id, pc_device_id, mobile_device_id,
                       bound_at, status}
```

- **密码联动**：手机与 PC 都用云端同账号登录，"改密/改用户名"任一端修改即全局生效，无需额外同步。
- **相互绑定**：在上述基础上增加一层**设备绑定关系**（`pc_device_id` ↔ `mobile_device_id`），由「扫码配对」建立（见 §6.6）；绑定后：
  - PC「个人中心」可见"已绑定手机"，手机「我的 → 设备绑定」可见"已绑定 PC"；
  - 采集/拍照数据可精确投递到该绑定关系对应的账号。
- **绑定与登录解耦**：允许「已登录但未绑定设备」（如仅手机上使用云功能），此时 P1-B 能力禁用。

## 3. 导航栏编排（方案 A）

> 结构：**底部五 Tab**——`首页 / 采集 / 拍照（中央凸起） / 消息 / 我的`
> 设计约束：①「采集 + 拍照 → 同步 PC」是本期核心，二者都必须是一级入口；②积分/充值下沉「我的」，首页仅保留只读积分卡；③设备绑定入口放「我的」，绑定结果同时反映在首页状态卡。

```
┌─────────────────────────────────────────────────────────────┐
│                        内容区（当前 Tab 页面）                │
└─────────────────────────────────────────────────────────────┘
┌──────────┬──────────┬──────────────┬──────────┬────────────┐
│   首页   │   采集   │   拍照 ●凸起 │   消息   │    我的    │
│  (home)  │(capture) │   (camera)   │ (inbox)  │  (mine)    │
│          │          │              │   ●红点  │            │
└──────────┴──────────┴──────────────┴──────────┴────────────┘
```

### 3.1 各 Tab 职责与页面层级

| Tab | 一级页面内容 | 二级页面 |
|-----|--------------|----------|
| **首页** `home` | 绑定状态卡（PC 在线/离线 + 已绑定设备）· 快捷动作（去采集 / 去拍照 / 去签到）· 积分卡（余额 + 签到入口）· 采集动态（最近采集/同步结果）· 公告横幅（未读公告摘要） | 公告详情、采集详情 |
| **采集** `capture` | 粘贴链接输入框（淘宝/1688/天猫/Temu）· 采集记录列表 · 同步状态（已入队/已同步/失败）· 分享采集引导（如何从电商 App 分享到本 App） | 采集记录详情、重新采集 |
| **拍照** `camera` | 相机 / 相册入口 · 归属商品组合选择 · 上传队列（待上传/中转中/已同步/已删除） | 拍照预览、商品组合选择、上传详情 |
| **消息** `inbox` | 公告列表 · 反馈回复列表 · 未读全部已读 | 消息详情（含图片）、反馈会话 |
| **我的** `mine` | 账号信息（用户名/邮箱/套餐）· **设备绑定**（扫码配对 / 解绑 / 查看已绑 PC）· 积分中心（签到 / 明细）· 在线充值（套餐 / 订单 / 流水）· 设置（主题 / 通知 / 服务器地址 / 退出登录） | 改密、改用户名、流水明细、订单详情、充值下单、签到记录 |

### 3.2 关键取舍（与备选方案的差异）

| 决策 | 理由 |
|------|------|
| **采集与拍照并列一级** | 二者都是"往 PC 送素材"，但入口不同（链接 vs 图片），分属两个 Tab 更符合心智 |
| **拍照居中凸起** | 呼应 N3 最高频动作，避免埋进子页 |
| **积分下沉「我的」** | 首页只放**只读积分卡 + 签到快捷入口**，避免首页过载；完整明细/充值在「我的 → 积分中心」 |
| **设备绑定放「我的」** | 首页状态卡显示绑定结果，绑定/解绑操作收敛到设置类入口 |
| **N6 广告视频预留** | Phase 1 不占导航位；后续在**首页新增「任务中心」卡位**承载"看视频得积分"，或将「积分中心」升级为一级临时 Tab |

> **备选方案 B**（首页 / 消息 / 拍照(凸起) / 积分 / 我的，采集并入首页）：优点是积分/签到/充值曝光更强；缺点是核心采集动作被降级为二级，与"手动转发/复制链接采集"的高频定位冲突。**本期采用方案 A**；若后续广告视频+积分成为核心商业化路径，再按上表方式演进到 B。

## 4. 通道 A 接口清单（云端直连，免 PC）

### 4.1 通用约定

| 项 | 约定 |
|----|------|
| 账号/计费基址 | `https://workbench.haocoming.top/auth-api` |
| 公告/反馈基址 | `https://workbench.haocoming.top/publish-api` |
| 认证头 | `Authorization: Bearer <token>`（会话接口） |
| 公告身份头 | `x-auth-token: <token>`（publish-api 专用） |
| 请求体 | JSON |
| 版本注入 | 计费类 POST 由服务端/代理自动注入 `app_version`（如 `1.5.2`） |
| 幂等 | 充值下单需带 `idempotency_key`（客户端生成 `idem_<uuid-no-dash>`） |
| 超时 | 建议 30s（对齐 Web 端 `REQUEST_TIMEOUT_MS = 30_000`） |

**错误语义**（来自 `handle_auth_error`）：

| HTTP | 含义 | App 处理 |
|------|------|----------|
| 401 | 未带 token / 会话已失效 / 远端会话缺失 | 清会话，跳登录页 |
| 400 | 参数错误（含登录失败、验证码错误） | 展示 `detail` |
| 403 | 无权限（如被踢下线的会话） | 展示 `detail`，引导重新登录 |
| 503 | 云端服务不可用（`CustomerAuthUnavailable`） | 展示「服务繁忙，请稍后重试」 |

> ⚠️ 与 Web 端一致：**裸 401 不一定代表会话失效**，只有 `detail` 命中会话失效文案时才清 token。App 端需移植该判定，避免误踢登录。

### 4.2 账号接口

| 方法 | 路径 | 请求体 | 响应 |
|------|------|--------|------|
| POST | `/api/customer/login` | 见下 | `{ok, user_id, token, expires_at, account}` |
| POST | `/api/customer/register` | `{username, email, email_code, password, invitation_code, role:"operator", workspace_code:"default", workspace_name:""}` | `{ok, message}` |
| POST | `/api/customer/activate` | `{...}`（激活） | `{ok, message}` |
| POST | `/api/customer/email-code` | `{email, purpose}` | `{ok, message}`（含有效期提示） |
| POST | `/api/customer/password-reset` | 见「找回密码」 | `{ok, message}` |
| POST | `/api/customer/forgot-password` | `{email}` | `{ok, message}` |
| POST | `/api/customer/reset-password` | `{email, code, new_password}` | `{ok, message}` |
| POST | `/api/customer/change-password` | `{account_id?/username?/email?, old_password, new_password}` | `{ok, message}` |
| POST | `/api/customer/change-username` | `{new_username, code}`（需 Bearer） | `{ok, message}` |
| POST | `/api/customer/logout` | 无（需 Bearer） | `{ok: true}` |
| GET | `/api/customer/me` | — | 会话信息（**不含 remote_token**） |

**`login` 请求体**（Web 端 `doLogin` 逻辑）：
- identifier 含 `@`（邮箱）→ `{email, password}`
- 否则（用户名）→ `{username, password}`
- 强制登录追加 `force: true`

**`login` 响应 `account` 字段**（`_public_account` 白名单，其余字段不暴露）：
`customer_id / username / email / account_status / login_status / role / workspace_code / workspace_name`

**`email-code` 的 `purpose` 取值**：`"register"` / `"reset_password"` / `"change_username"`

**找回密码流程**：
1. `POST /email-code` body `{email, purpose:"reset_password"}`
2. `POST /reset-password` body `{email, code, new_password}`

**单端登录语义（重要）**：
- 服务端单端登录，新登录会 `revoke` 旧 session。
- 登录失败若返回「已在其他设备登录」，**必须给出「强制登录」入口**（重试并带 `force:true`），否则用户被锁死约 5 分钟。
- ⚠️ **与 N1 的冲突点**：PC 与手机若共用同一账号，**单端登录会导致互相顶下线**。需云端支持"多设备并存"（或为移动端单独发放长期 device session）。**列为 N1 前置依赖**，见 §7 R8。
- `logout` 会联动撤销云端登录态。

### 4.3 计费 / 积分 / 充值 / 订单接口（含 N4 签到）

| 方法 | 路径 | 关键参数 | 响应要点 |
|------|------|----------|----------|
| GET | `/api/customer/billing/summary` | — | 见 §4.3.1 |
| GET | `/api/customer/billing/usage` | `cursor, limit(≤100)`，可选 `feature_key, usage_status, date_from, date_to` | `{ok, items[], next_cursor, has_more}` |
| GET | `/api/customer/billing/ledger` | `category(""|"topup"|"reward"), limit, offset` | `{ok, items[], total, limit, offset, has_more, point_unit_scale}` |
| POST | `/api/customer/billing/topup-orders` | `{provider:"alipay", package_id, amount_cents?, idempotency_key}` | `TopupOrderResponse` 见 §4.3.2 |
| POST | `/api/customer/billing/topup-quote` | `{amount_cents}` | `{ok, product: BillingPackage}` |
| POST | `/api/customer/billing/plan-basic/claim` | 无 | `{ok, claimed_points, claim_count, claim_max, period}` |
| POST | `/api/customer/billing/daily-extra/claim` | 无 | `{ok, claimed_points, claim_count, period, next_claim_at, first_claim_bonus}` |
| GET | `/api/customer/billing/station-binding` | — | `{bound, station_code, station_name, change_count, can_change, next_change_at, remaining_seconds}` |
| POST | `/api/customer/billing/station-binding` | `{station_code}` | 绑定结果 |
| GET | `/api/customer/station-partners` | — | 分站列表 |
| GET | `/api/customer/station-partners/{station_code}` | — | `StationTier[]`（`{amount_cents, rate}`） |

> **签到（N4）**：体验版/基础版走 `plan-basic/claim`（周期领取），日常走 `daily-extra/claim`（每日额外积分）。两者均可判断"今日是否可领"：`wallet.plan` 中 `basic_claimable / daily_claimable / daily_next_claim_at`。
> **N6 预留**：未来广告视频奖励可在 `billing/ledger` 的 `source_type` 上扩展新类型（如 `ad_reward`），移动端仅需展示，不需改接口形态。

#### 4.3.1 `billing/summary` 核心结构（客户端可直接照搬 TS 类型）

```
BillingSummary {
  ok
  account   { account_id, username, workspace_id, workspace_code }
  wallet {
    points_balance, locked_points, manual_frozen_points, frozen_points,
    available_points, version, ledger_head_hash, updated_at,
    plan {
      plan_type: "experience"|"flagship"|string
      plan_label, plan_balance, plan_limit, plan_used, next_refresh_at, plan_expire_at
      basic_claim_points, basic_claim_count, basic_claim_max, basic_claimable
      daily_claim_points, daily_claimable, daily_claim_date, daily_first_claim_bonus,
      daily_week_count, daily_week_max, daily_next_claim_at
      extra_balance
    }
  }
  pricing { currency:"CNY", rule_version, point_unit_scale, points_per_cny,
            ratio_label, product_link{...}, features{}, min_client_version, effective_at }
  topup_products: BillingPackage[]
  topup_promotion?: { name, bonus_rate_percent, tiers[], applies_to:"fixed_packages", active:true }
  recent_ledger:  BillingLedgerEntry[]
  recent_orders:  BillingOrder[]
  pending_order?: BillingOrder | null      // 支付中订单，仅一条，用于轮询识别到账
  security { server_authoritative, local_balance_trusted, ledger_hash_chain,
             settlement_requires_signed_provider_callback }
}
```

- `BillingPackage`：`{package_id, label, amount_cents, points?, base_points?, promotion_bonus_points?, promotion_bonus_percent?, total_points?}`
- `BillingOrder`：`{order_id, out_trade_no, provider:"wechat"|"alipay", package_id, amount_cents, currency, status:"pending"|"paid"|"closed"|"failed"|"refunded", created_at, paid_at, expires_at, ...points}`
- `BillingUsageEntry`：`{usage_id, feature_key, billing_profile, source_ref, reserved_points, charged_points, refunded_points, status:"reserved"|"succeeded"|"failed"|"frozen", provider, model, input_tokens, output_tokens, total_tokens, error_message, created_at, settled_at, rule_version, task}`
- `BillingLedgerItem`：`{entry_id, points_delta, balance_after, source_type, source_id, created_at}`

> 「订单」在 App 里由 `recent_orders` + `pending_order` 承担；「流水」由 `recent_ledger`（概览）与 `billing/ledger`（分页明细，仅 credit）承担。

#### 4.3.2 充值下单响应

```
TopupOrderResponse {
  ok, reused
  order: BillingOrder
  payment {
    provider: "alipay"
    mode: "gateway_not_configured" | "native_qr" | "page_pay"
    qr_code_url, pay_url, message
  }
}
```

- `mode = native_qr`：App 内展示二维码，用户用支付宝扫码。
- `mode = page_pay`：App 内 `WebView` 打开 `pay_url`。
- `mode = gateway_not_configured`：提示不可用。
- 客户端**不得自行推算赠送规则**，自定义金额必须走 `topup-quote` 取服务端报价。

### 4.4 消息中心 / 公告（publish-api，含 N2 定向下发）

**现状（关键风险点）**：
PC 端的 `/api/messages/*` 是**本地 SQLite 表**，由两个后台同步服务定时从 publish-api 拉取后落库：

| 后台服务 | 拉取地址 | 间隔 | 身份 |
|----------|----------|------|------|
| `AnnouncementSyncService` | `GET {publish-api}/api/announcements/public` | 300s | `x-auth-token`（或 `?account_id=` 兜底） |
| `AnnouncementSyncService._sync_pending_images` | `GET {publish-api}/api/announcements/{server_id}/images` | — | 同上 |
| `FeedbackReplySyncService` | `GET {publish-api}/api/feedback-replies/public` | 180s | `x-auth-token` |

**本地消息接口**（**App 免 PC 时不可用**，此处仅作语义参照）：
`GET /api/messages`、`GET /api/messages/unread-count`、`POST /api/messages/read-all`、`POST /api/messages/{id}/read`、`DELETE /api/messages/{id}`、`POST /api/messages/sync`

消息数据模型（供 App 端对齐字段）：
`{id, serverId, title, content, publishedAt, read, kind, imageCount, imageRev, images[]}`
> 注意：`read` 字段上游可能返回 `true|1|"1"|"true"`，**必须归一化**，否则红点/未读态失效。

**P1-A 结论**：App 免 PC 场景**直接对接 publish-api 的三个 public 接口**（带 `x-auth-token`），自行维护「已读」本地表（`server_id` 去重）。
- **N2 定向下发的可行性**：后台对"指定用户"发公告，本质是按 `account_id` 定向；由于 PC 与手机使用**同一 `account_id`（N1）**，同一条定向公告会**同时**被 PC 的 `AnnouncementSyncService` 和移动端的直连轮询取到，从而"同时提示 PC 账号与移动端账号"。**无需新增通道，只需云端保证按 `account_id` 过滤正确**。
- publish-api 无推送能力，P1 **只能轮询**（建议 3~5 分钟，与 PC 端 180/300s 对齐）；真正的推送依赖 P1-B 或云端新增推送网关（R3）。
- 字段样例见**附录 B**。

### 4.5 设备绑定接口（N1，**新增，云端待建**）

> 当前**不存在**任何 `/api/customer/device*` 或 `/binding*` 接口。以下为建议契约，需云端落地后方可实现。

| 方法 | 路径 | 请求体 | 响应 |
|------|------|--------|------|
| POST | `/api/customer/device/pairing-code` | `{device_type:"pc"\|"mobile", device_id, device_name}`（需 Bearer） | `{ok, pair_code, qr_payload, expires_at}`（PC 端展示二维码） |
| POST | `/api/customer/device/bind` | `{pair_code, device_id, device_name, device_type}`（需 Bearer） | `{ok, binding:{binding_id, account_id, devices:[...]}, message}` |
| GET | `/api/customer/device/bindings` | —（需 Bearer） | `{ok, items:[{binding_id, pc_device_id, pc_device_name, mobile_device_id, mobile_device_name, bound_at, status}]}` |
| DELETE | `/api/customer/device/bindings/{binding_id}` | —（需 Bearer） | `{ok, message}` |

- 「相互绑定」= 一条 binding 同时含 `pc_device_id` 与 `mobile_device_id`；PC 与手机各查一次 `GET /bindings` 即双向可见。
- 配对码短时效（建议 ≤5 分钟）、一次性消费。

### 4.6 拍照短期中转接口（N3，**新增，云端待建**）

> 当前**无**移动端拍照上传端点。为满足「服务器仅短期存储、同步到对应账号后删除」，建议采用**中转箱（inbox）**模型：

| 方法 | 路径 | 请求体 | 响应 |
|------|------|--------|------|
| POST | `/api/customer/capture/uploads` | `{account_id 隐含于 token, bundle_ref?, file_name, content_type, size_bytes, sha256}`（需 Bearer） | `{ok, upload_id, upload_url, expires_at}`（返回预签名直传地址） |
| PUT | `{upload_url}` | 二进制（直传对象存储，不经业务服务） | 204 |
| POST | `/api/customer/capture/uploads/{upload_id}/commit` | `{bundle_ref, note?}` | `{ok, status:"pending"}` |
| GET | `/api/customer/capture/inbox` | `?after=&limit=`（**PC 侧拉取**，需 Bearer） | `{ok, items:[{upload_id, account_id, bundle_ref, size_bytes, created_at, status}]}` |
| POST | `/api/customer/capture/inbox/{upload_id}/ack` | `{result:"delivered"\|"failed"}`（**PC 拉取成功后确认**） | `{ok, deleted:true}` |
| GET | `/api/customer/capture/uploads/{upload_id}` | —（移动端查状态） | `{ok, status:"pending"\|"delivered"\|"deleted"\|"expired", expires_at}` |

**生命周期（强制约束）**：

```
拍照 → 预签名直传（短期对象存储）
     → commit（status=pending，写 TTL，建议 24h）
     → PC 轮询 inbox 拉到本地「商品组合」
     → PC 调 ack(delivered)
     → 服务端立即删除对象 + 标记 deleted
     （若超时未 ack → TTL 到期自动清理，status=expired）
```

- 移动端上传队列状态直接映射 `pending / delivered / deleted / expired`（对照 §3.1 拍照 Tab）。
- **PC 拉取即删**：`ack` 是删除的唯一正常触发路径，避免"删除早于同步完成"。
- 若走局域网直传（PC 在线），可跳过云端中转，直接投递到 PC 草稿池（复用 §5.2 `/plugin/product-capture/draft`）。

## 6. Flutter 技术方案

### 6.1 工程结构（建议）

```
lib/
├─ main.dart
├─ app/                     # 路由、主题、i18n
│  └─ shell/                # 底部导航 Shell（方案 A 五 Tab）
├─ core/
│  ├─ http/                 # 双 BaseUrl Client（cloud / lan）
│  ├─ error/                # toUserMessage 错误文案映射（移植 Web 端）
│  ├─ storage/              # token / account 安全存储
│  └─ session/              # 会话语义、单端登录、强制登录
├─ features/
│  ├─ auth/                 # 登录/注册/找回/改密
│  ├─ home/                 # 首页（状态卡 / 积分卡 / 公告横幅）
│  ├─ billing/              # summary / 充值 / 订单 / 流水 / 签到领取
│  ├─ inbox/                # 消息中心（publish-api + 本地已读表）
│  ├─ taskboard/            # 任务看板 + 轻审核（局域网）
│  ├─ capture/              # 分享采集（局域网）
│  ├─ camera/               # 拍照上传（云端中转 + 局域网直传）
│  ├─ device/               # 设备绑定（扫码配对 / 解绑）
│  └─ settings/             # 服务器地址、配对、退出
└─ shared/                  # 通用组件/模型
```

### 6.2 导航实现（方案 A）

- 使用 `Scaffold + BottomNavigationBar`（或 `NavigationBar`）+ `IndexedStack` 保持各 Tab 状态。
- **中央凸起**：用 `FloatingActionButtonLocation.centerDocked` + `BottomAppBar`，或自定义 `CustomPainter` 实现 notch；拍照按钮单独唤起（可全屏相机或 `bottomSheet`）。
- **消息红点**：由 `inbox` 的未读计数驱动 `Badge`（对齐 `GET /api/messages/unread-count` 语义，App 端自算 publish-api 未读）。
- **深链 `home → camera`**：首页"去拍照"快捷动作需切换 Tab 而非 push，统一走 shell 的 `selectTab(index)`。

### 6.3 网络层

- **双 Client 设计**：
  - `CloudClient`：baseUrl = `auth-api`（或 `publish-api`），永远可用。
  - `LanClient`：baseUrl = `http://<PC-IP>:8010`，可切换/失效降级。
- 复用 Web 端语义：
  - Token 存 `SharedPreferences` + `flutter_secure_storage`（敏感），对齐 Web 端 `wh_demo_token` / `wh_demo_account` 的语义拆分。
  - 请求拦截器统一注入 `Authorization: Bearer`、`app_version`、`idempotency_key`。
  - 响应拦截器移植 `toUserMessage(raw)` 的**中→英/中 错误映射表**（邀请码、邮箱验证码、登录失败次数、session revoked、余额不足、并发冲突等），保证 App 与 Web 文案一致。
- 局域网 IP 字面量需跳过证书校验（对齐后端 `is_ip_literal_host` 逻辑）。

### 6.4 鉴权与会话

- 登录成功：存 `token` + `account`，随后触发消息同步（`syncMessages`）。
- **单端登录**：捕获「已在其他设备登录」→ 展示「强制登录」按钮 → 重试带 `force:true`。
- ⚠️ **N1 前置**：PC/手机同账号共用时的互踢问题需云端支持多设备并存（R8）。
- **会话失效判定**：仅当 401 且 `detail` 命中会话失效文案才清 token，避免误踢。
- 退出：调 `/api/customer/logout` 联动撤销云端登录态。

### 6.5 支付（支付宝）

- 流程：`billing/summary` → 选套餐 → `topup-orders`（带幂等键）。
- `native_qr`：App 内渲染二维码（`qr_flutter`）。
- `page_pay`：`webview_flutter` 打开 `pay_url`。
- 到账识别：下单后轮询 `billing/summary`，观察 `pending_order` 消失 + `wallet.points_balance` 增长，或 `recent_orders` 中该单变 `paid`。
- **关键风险**：服务端默认支付宝回跳地址为 `http://127.0.0.1:8010/?module=personal_center&payment=success`，**手机无法访问该地址**。需服务端支持「自定义 return_url / 无回跳 + 纯轮询确认」，否则支付成功页在手机上会跳到失败页（不影响实际到账，但体验受损）。**必须在 P1-A 启动前与后端确认。**

### 6.6 局域网配对 + 设备绑定（合并扫码）

1. PC 工作台展示二维码，payload 同时含：`IP:PORT`（局域网直连）+ `pair_code`（云端设备绑定，§4.5）。
2. App 用 `mobile_scanner` 扫码 → 两步：① 调 `POST /api/customer/device/bind` 建立账号级双向绑定；② 探活 `GET /api/customer/me` 校验局域网连通。
3. 保存到本地，下次自动重连；失败提示「请确认 PC 工作台已开启且在同一局域网」。

### 6.7 分享采集

- 用 `receive_sharing_intent` 注册 Android **Share Target**（Temu/淘宝/1688/天猫分享 → 本 App）。
- 收链后走 B 通道：`plugin-sessions` → `plugin/session/{id}` WS 或 `plugin/poll`，把链接登记进采集队列。
- 无 PC 在线时：本地暂存链接，PC 恢复后补登记。

### 6.8 拍照上传

- 相机/相册 → 压缩 → 选择归属「商品组合」→ 上传。
- **双路径**：
  - PC 在线 → 局域网直传 `/plugin/product-capture/draft`。
  - PC 离线 → 走 §4.6 云端短期中转，PC 上线后拉取并 `ack` 触发删除。
- App 侧展示上传队列状态（`pending / delivered / deleted / expired`）。

## 附录 B：publish-api 公告 / 反馈回复字段样例

> 用途：移动端免 PC 直连 publish-api 时的字段对齐依据（对应 §4.4）。以下为**依据 PC 端同步服务消费逻辑推断的结构**，落地前需以云端实际返回为准。

### B.1 公告列表 `GET {publish-api}/api/announcements/public`

请求头：`x-auth-token: <token>`
可选查询：`?account_id=<id>`（token 缺失时的兜底）

```json
{
  "ok": true,
  "items": [
    {
      "id": 1024,
      "title": "平台维护通知",
      "content": "今晚 22:00-23:00 系统维护……",
      "kind": "notice",
      "published_at": "2026-10-08T10:00:00+08:00",
      "account_id": null,
      "image_count": 2,
      "image_rev": 3,
      "read": 0
    }
  ]
}
```

字段说明：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | int | 云端消息唯一 ID（对应本地 `serverId`，App 端去重键） |
| `title` / `content` | string | 标题 / 正文（正文可能含换行） |
| `kind` | string | 消息类型（如 `notice`）；App 端按类型决定图标 |
| `published_at` | ISO8601 | 发布时间（带时区） |
| `account_id` | int \| null | **`null` = 全员公告；非空 = 定向公告**（N2：仅该账号的 PC 与移动端可见） |
| `image_count` / `image_rev` | int | 图片数量 / 版本号（用于判断是否需要重新拉图） |
| `read` | `true\|1\|"1"\|"true"` | **必须归一化**，上游类型不固定 |

### B.2 公告图片 `GET {publish-api}/api/announcements/{server_id}/images`

```json
{
  "ok": true,
  "rev": 3,
  "images": [
    { "name": "a.png", "url": "https://.../a.png", "content_type": "image/png", "size": 204800 }
  ]
}
```

> App 端可本地缓存图片（按 `server_id + rev`），`rev` 变化时重拉。

### B.3 反馈回复 `GET {publish-api}/api/feedback-replies/public`

请求头：`x-auth-token: <token>`

```json
{
  "ok": true,
  "items": [
    {
      "id": 77,
      "feedback_id": 12,
      "content": "您反馈的问题已处理……",
      "created_at": "2026-10-08T11:30:00+08:00",
      "read": "1"
    }
  ]
}
```

### B.4 移动端对齐要点

- **去重键**：一律用云端 `id`（本地 `serverId`），保证 PC 与手机看到的是同一条。
- **已读状态**：publish-api 的 `read` 不可依赖（PC 与手机各自维护），App 端自建 `server_id → read` 本地表。
- **定向公告隐私（R11）**：客户端**不得**在无 token 时用 `account_id` 裸查他人公告；服务端需强制按 token 归属过滤。
