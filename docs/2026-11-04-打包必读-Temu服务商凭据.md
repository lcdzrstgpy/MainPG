# 打包必读：Temu 服务商凭据（安装包**不携带**）

> 给负责打包的人看。结论一句话：**安装包里一个凭据都不放，打包机上也别放。**

## 一句话

服务商那对 `yl_client` / `yl_token` 只存在**服务器**（`/etc/wh-workbench/auth.env`）。
客户端登录后自己向服务器要，加密存本机。**安装包里不带、也不需要带。**

## 打包时你只需要

照常打包，什么都不用配：

```powershell
powershell -ExecutionPolicy Bypass -File build_installer.ps1 -Version 1.2.3
```

日志里会有一行确认：

```
[build] no Temu provider credentials bundled (fetched from the customer center after login)
```

## 如果你手上有 temu_gateway.local.json，打包会**直接报错**

```
Refusing to build: ...\wh_local\data\temu_gateway.local.json exists.
Temu provider credentials must NOT be bundled ...
```

这不是毛病，是刻意的。处理方式：**删掉或改名**这个文件，再打。

为什么这么硬：安装包能被解包，密钥就写在程序里（`wh_local/secrets.py`），程序还自带解密命令 —— 打包进去等于把**全系统共用**的凭据发给每个用户，一份包流出去所有人都受影响，而且收不回来。

## 三道防线（都已生效）

| 拦什么 | 行为 |
|---|---|
| `temu_gateway.local.json` 在打包机上存在 | 构建直接失败（见上） |
| `temu_gateway.enc` 出现在产物目录 | 构建前先删掉；若仍出现 → 报错（禁止打包） |
| `temu_gateway.json` 模板里 `yl_client`/`yl_token` 非空 | 直接报错（模板必须为空） |

## 用户装完之后

| 场景 | 表现 |
|---|---|
| 登录后打开「Temu 发布」页 | 自动从服务器取凭据，落本机（加密）→ 之后**离线也能用** |
| 没登录 / 离线 | 提示「还没拿到 —— 登录后打开本页会自动获取」 |
| 换机器 | 登录一次即可，不用重新配 |

服务器没配 `WH_TEMU_YL_CLIENT` / `WH_TEMU_YL_TOKEN` 时，接口返回 503，客户端静默退回「没拿到」，不影响其它功能。

## 换凭据 = 只改服务器（这就是「作废开关」）

1. 让服务商重置 token
2. 改服务器 `/etc/wh-workbench/auth.env` 的两个值，重启 `wh-customer-auth`
3. 完事

已装机的客户端会比对这对凭据的**指纹**，发现变了就自动覆盖本地那份（最迟 5 分钟内；用户再点一次发布也会立刻触发）。**不用重新打包、不用让用户手填、不用重装。**

如果用户此时正好在发布，会收到一句明确的提示：「服务商凭据已过期，已自动更新为服务器上的最新值 —— 请再点一次提交发布」。

## 本地开发

想在开发机跳过服务器直接用某对凭据：在该目录下建 `temu_gateway.local.json`（已 `.gitignore`），明文优先。

**但别把它留在打包机上** —— 打包会失败。用完删掉。

它只对本机生效；服务器下发成功后会写进本人库（优先级更高）。

## 附：为什么不再做「加密随包」

之前实现过 `temu_gateway.enc`（AES-256-GCM），评估后撤掉，原因：

| 攻击 | `.enc` 能否挡住 |
|---|---|
| 安装包里 `grep` / `strings` 搜凭据 | ✅ 挡得住 |
| 解包后翻出固定密钥、跑 `python -m wh_local.secrets decrypt` | ❌ 挡不住，几分钟的事 |

密钥必须跟着程序走（客户机要用），所以「加密随包」只能算混淆。既然一样挡不住，就不如干脆不带 —— 包里没有，才是真的没有。

（`cos.enc` / `onebound.enc` 是既有设计，不受本次调整影响；它们的轮换方式仍是重新打包。）
