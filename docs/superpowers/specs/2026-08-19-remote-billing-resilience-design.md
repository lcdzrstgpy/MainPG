# 远端计费链路容错设计

## 背景

远端计费移植后，商品处理新增了任务余额预检、逐商品文本/图片用量预留、AI 网关调用和结算。当前客户端对远端 TLS/网络错误采用单次请求即失败；商品线程最多 8 路并行，因此远端短暂抖动会被放大为整批失败。修复不得绕过计费，不得把服务端密钥放回本地，也不得修改万邦采集链路。

## 方案

采用“幂等重试 + 统一并发闸门 + 减少重复预检”的本地韧性方案：

1. `CustomerAuthClient` 仅对计费读取及具备幂等标识的预留/结算请求重试。最多 3 次，使用短指数退避；401/402/403、其他确定性 4xx 和协议错误不重试。
2. 远端计费请求和产品 AI 网关请求分别共用小并发闸门，各最多 2 路，避免 8 个商品线程同时冲击同一远端主机。
3. 任务创建时只读取一次余额，并将该结果传给同一入口内的重复计费检查；逐商品仍按权威服务端接口预留，保持积分安全边界。
4. 文本 AI 网关继续使用现有三次上层重试，图片识别继续使用现有两次上层重试；仅增加共享并发闸门，不叠加新的重试层。服务端现有请求哈希与用量账本负责去重。
5. 前端把远端计费 503 与 API Key/余额错误分开提示，明确为“服务器计费服务暂时不可用，可稍后重试”。

## 错误与安全边界

- 不重试登录、注册、充值下单等非计费处理请求。
- 不生成新的幂等键；每次重试复用原请求 payload、`idempotency_key` 或 `usage_id`。
- 重试耗尽后继续返回稳定、脱敏的 503/AI 暂不可用错误，不持久化 token 或底层 TLS 诊断。
- 不降级为本地 API Key，不绕过余额检查、用量预留或结算。

## 验证

- 单元测试先复现一次 TLS/网络失败即终止，再验证瞬时失败后成功、确定性 4xx 不重试、三次耗尽、并发不超过 2。
- 产品处理测试验证同一任务不重复查询余额，远端不可用提示不再归类为 API Key。
- 运行全部 `test_product_processing_*.py`、客户计费相关测试、前端相关测试与构建检查。
