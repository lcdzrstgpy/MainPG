# 安卓伴侣 App · 云端需求说明

> 提出方：移动端（安卓伴侣 App）
> 接收方：云端 / 后端（`auth-api` + `publish-api`）
> 日期：2026-10-08
> 关联文档：[第一阶段接口清单与技术方案](./2026-10-08-安卓伴侣App-第一阶段接口清单与技术方案.md)

## 0. 背景与目标

安卓伴侣 App 定位为 PC 工作台的随身延伸，需与 PC 端**共用同一云端账号体系**。当前云端已有完整的账号 / 计费 / 充值 / 公告能力，移动端可直接复用；但以下 **4 项能力云端尚不具备或存在阻塞**，需云端配合落地。

| 编号 | 需求 | 优先级 | 阻塞关系 |
|------|------|--------|----------|
| C1 | 多设备并存会话（解除单端登录互踢） | **P0** | 阻塞全部移动端在线场景 |
| C2 | 设备绑定（手机 ↔ PC 相互绑定） | **P0** | 阻塞"账号绑定"核心诉求 |
| C3 | 拍照短期中转 + 同步即删 | P1 | 阻塞拍照上传功能 |
| C4 | 定向公告按 `account_id` 正确过滤 | P1 | 阻塞"按绑定用户下发"体验 |
| C5 | 支付宝支付回跳地址可配置 | P1 | 影响充值体验（非阻塞） |

---

## C1（P0）多设备并存会话

### 现状问题

云端为**单端登录**：新登录会 `revoke` 旧 session。PC 与手机使用**同一账号**时，手机登录会把 PC 顶下线，PC 登录又会把手机顶下线，双方互相锁死（且被顶替后需 `force:true` 才能自救）。

### 需求

允许**同一账号在 PC 与移动端同时保活**，至少满足：

1. 移动端登录**不撤销** PC 端会话，反之亦然。
2. 按**设备类型（`pc` / `mobile`）**维度做会话隔离，同一类型内仍保持单端（防账号共享）。
3. 会话记录中携带 `device_type` / `device_id`，供 C2 与公告投递使用。

### 建议方案（择一）

- **方案 A（推荐）**：会话表增加 `device_type` 维度，`revoke` 范围由"全账号"收窄为"同 device_type"。
- **方案 B**：为移动端发放**独立长期 device session**（与 Web/PC session 并行）。

### 验收标准

- 手机登录后，PC 端 `GET /api/customer/me` 仍返回有效会话。
- 同一设备类型二次登录仍会踢掉该类型内的旧会话。

## C2（P0）设备绑定：手机 ↔ PC 相互绑定

### 需求

在**同一账号**基础上，建立"PC 设备 ↔ 移动设备"的绑定关系，实现双向可见：

- PC 端可看到"已绑定的手机"；手机端可看到"已绑定的 PC"。
- 后续采集 / 拍照数据可按绑定关系精确投递。

### 建议契约（可按云端规范调整）

| 方法 | 路径 | 请求体 | 响应 |
|------|------|--------|------|
| POST | `/api/customer/device/pairing-code` | `{device_type, device_id, device_name}` | `{ok, pair_code, qr_payload, expires_at}` |
| POST | `/api/customer/device/bind` | `{pair_code, device_id, device_name, device_type}` | `{ok, binding, message}` |
| GET | `/api/customer/device/bindings` | — | `{ok, items:[{binding_id, pc_device_id, pc_device_name, mobile_device_id, mobile_device_name, bound_at, status}]}` |
| DELETE | `/api/customer/device/bindings/{binding_id}` | — | `{ok, message}` |

### 约束

- 配对码**短时效（≤5 分钟）+ 一次性消费**。
- 绑定必须**校验双方属于同一 `account_id`**，禁止跨账号绑定。
- 解绑需即时生效，移动端/PC 端下次拉取即不可见。

### 验收标准

- PC 生成配对码 → 手机扫码绑定成功 → PC 与手机的 `GET /bindings` 均能看到对方。
- 解绑后双方列表同步移除。

## C3（P1）拍照短期中转 + 同步即删

### 需求

移动端拍照上传后，云端**仅作短期中转**；PC 拉取成功后**立即删除**，不做长期存储。

### 建议契约（中转箱模型）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/customer/capture/uploads` | 申请上传，返回预签名 `upload_url` + `expires_at` |
| PUT | `{upload_url}` | 直传对象存储（不经业务服务） |
| POST | `/api/customer/capture/uploads/{upload_id}/commit` | 提交，`status=pending` |
| GET | `/api/customer/capture/inbox` | **PC 侧**拉取待同步列表 |
| POST | `/api/customer/capture/inbox/{upload_id}/ack` | **PC 侧**确认已拉取 → 云端删除对象 |
| GET | `/api/customer/capture/uploads/{upload_id}` | 移动端查状态 |

### 生命周期（强制）

```
上传 → commit(pending) → PC 拉取 inbox → PC ack(delivered) → 立即删除对象
                          （超时未 ack → TTL 到期清理，status=expired）
```

### 约束

- **TTL 建议 ≤24h**，到期自动清理并标记 `expired`。
- **仅 `ack` 触发正常删除**，避免"删除早于同步完成"；`ack` 需**幂等**。
- 单文件大小上限、并发数上限需云端给定。
- 对象存储需支持预签名直传（避免大图过业务服务）。

### 验收标准

- PC `ack` 后 `GET /api/customer/capture/uploads/{id}` 返回 `deleted`，对象存储中文件已不存在。
- 超过 TTL 未 ack 的文件被自动清理。

## C4（P1）定向公告按账号正确过滤

### 现状

`publish-api` 已有 `GET /api/announcements/public`，PC 端 `AnnouncementSyncService` 定时拉取。移动端将**复用同一接口**（带 `x-auth-token`）。

### 需求（确认 + 加固）

1. 后台对"指定用户"发公告时，需按 `account_id` 定向；该账号的 **PC 端与移动端都能拉到同一条**。
2. **必须强制按 token 归属过滤**：禁止客户端在无 token 时用 `?account_id=` 裸查他人定向公告（越权/隐私风险）。
3. 返回体需包含 `account_id`（`null` = 全员公告），字段样例见第一阶段文档附录 B。

### 验收标准

- 账号 A 的定向公告，账号 B 拉取时**不可见**。
- 同一账号在 PC（同步服务）与手机（直连）都可见。

## C5（P1）支付宝支付回跳地址可配置

### 现状问题

服务端默认支付宝回跳地址为 `http://127.0.0.1:8010/?module=personal_center&payment=success`，**手机无法访问**，支付成功后体验受损（不影响实际到账）。

### 需求（择一）

- 支持**自定义 `return_url`**（移动端传入可达地址），或
- 提供**无回跳模式**，由客户端纯轮询确认到账。

### 验收标准

- 移动端发起充值后，不因回跳不可达而跳转失败页。
