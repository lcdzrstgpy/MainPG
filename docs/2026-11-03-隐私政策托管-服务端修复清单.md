# 隐私政策服务端托管 — 修复清单（2 项）

> 提交方：客户端（MainPG/web-frontend）
> 接收方：服务端（wh-admin / nginx）
> 日期：2026-11-03
> 范围：只针对已上线的 `https://workbench.haocoming.top/privacy` 与 `*.json/.md` 接口，不涉及后台 UI、数据目录与 nginx 结构。
> 结论先说：接口与内容都已经可用（11 个章节、锚点、ETag/304、CORS 都验过），下面 2 条是**实现方式**上的问题，不影响主流程，但影响「禁用 JS / 抓取 / 合规存档」三个场景。

---

## 问题 1：`/privacy.md` 返回的是 HTML，不是 Markdown

### 证据

```bash
$ curl -sI https://workbench.haocoming.top/privacy.md | grep -i content-type
content-type: text/markdown; charset=utf-8

$ curl -s https://workbench.haocoming.top/privacy.md | head -3
<h2 id="intro">前言</h2>

<p class="lead">欢迎您使用界野（下称"我们"）。……
```

Content-Type 声明是 `text/markdown`，正文却是预渲染后的 HTML 片段。

### 影响

1. **兜底链路是断的**：`/privacy` 页面的 `<noscript>` 写的是

   > 本页面需要 JavaScript 渲染。可改用 <a href="/privacy.md">纯文本版本</a> 阅读。

   禁用 JS 的用户按提示点过去，拿到的是 HTML 源码（浏览器会按文本渲染成一堆标签），不是可读政策。
2. **抓取/存档工具误判**：依 Content-Type 解析 Markdown 的工具会把 `<h2>` 当成纯文本内容，得到的是标签而非正文。
3. 合规存档、第三方审计、搜索引擎抽取时无法直接使用该端点。

### 修复方案

**方案 A（推荐，改一处返回内容）**

`/privacy.md` 返回**原始 Markdown**（`data/privacy-policy/current.md` 的内容），Content-Type 用 `text/markdown; charset=utf-8`，或为兼容性用 `text/plain; charset=utf-8`（浏览器直接预览体验更好）。

```python
@app.get("/privacy.md", include_in_schema=False, response_class=PlainTextResponse)
def public_privacy_markdown():
    if not meta.get("published"):
        raise HTTPException(404)
    return PlainTextResponse(markdown_text, media_type="text/markdown; charset=utf-8")
```

**方案 B（原始 Markdown 没保留时）**

把路由改名 `/privacy.txt`，返回去掉标签后的纯文本，并同步把 `/privacy` 里 `<noscript>` 的链接改过去。**不要**继续用 `.md` 后缀返回 HTML——后缀与 Content-Type 都在暗示这是 Markdown。

### 验收

```bash
# 1) Content-Type 正确
curl -sI https://workbench.haocoming.top/privacy.md | grep -i content-type
#   期望：text/markdown; charset=utf-8 或 text/plain; charset=utf-8

# 2) 正文是 Markdown 而不是 HTML
curl -s https://workbench.haocoming.top/privacy.md | head -5
#   期望：以 "# 界野隐私政策" 或 "## 前言 {#intro}" 之类开头；不含 "<h2"、不含 "<p class="

# 3) 禁用 JS 打开 /privacy → 点 noscript 里的链接 → 能看到可读的中文正文
```

## 问题 2：`/privacy` 正文靠 JS 注入，禁用 JS 时是空页

### 证据

页面 `<body>` 里没有正文，正文是一段内联脚本里的字符串，再由 `innerHTML` 写进去：

```html
<script>
  (function () {
    var markdown = "<h2 id=\"intro\">前言<\/h2>\n\n<p class=\"lead\">欢迎您使用界野……
```

把 `<script>` 段整体剔除后，页面剩余可见文本只有 126 个字符——即 `<noscript>` 那句「本页面需要 JavaScript 渲染」。

### 影响

1. **SEO**：抓取器通常不执行这段内联注入（或按白名单跳过 script），正文索引不到。
2. **法务存档 / 截图取证**：很多存档工具、打印服务、无障碍阅读器默认禁用脚本，会得到空页。
3. 与设计文档 4.3「服务端渲染 Markdown，首屏即完整 HTML」不符；现在的实现等于把渲染结果又绕回客户端注入，等于多做了一步。

### 修复方案

模板里已经有**渲染好的 HTML 字符串**（就是上面那个 `var markdown` 的值），直接把它写进 `<article>` 容器即可，不需要改渲染逻辑：

```diff
-      <article class="doc" id="doc">
-        <div class="doc-loading">正在加载协议…</div>
-      </article>
+      <article class="doc" id="doc">
+        __CONTENT_HTML__
+      </article>
```

```diff
-<script>
-  var markdown = "<h2 id=\"intro\">前言……";
-  (function () { doc.innerHTML = markdown; … })();
-</script>
+<script>
+  // 只保留目录高亮 / 滚动定位这类渐进增强，不再注入正文
+  (function () { … })();
+</script>
```

注意事项：

- 模板替换处**只做一次替换，不要再做 HTML 转义**（内容已含 `<h2 id="intro">`、`<p class="hl">`、`<em>/<u>/<strong>`，二次转义会显示成标签文本）。
- 11 个锚点 id 必须保持：`intro / collect / storage / security / use / share / rights / change / minor / other / contact`（旧外链在客户端、公告、邮件里都用过）。
- 目录仍从渲染后的 `h2` 生成；`IntersectionObserver`/滚动高亮脚本保留即可。
- `<noscript>` 可以保留一句「本页无需 JavaScript 也可阅读」，也可以直接删掉。

### 验收

```bash
# 1) 剔除 script 后仍有正文：11 个 h2 + 关键词
curl -s https://workbench.haocoming.top/privacy \
  | python3 -c "import sys,re;h=re.sub(r'<script.*?</script>',' ',sys.stdin.read(),flags=re.S);print('h2:',len(re.findall(r'<h2',h)));print('kw:', '不采集、不存储终端消费者的个人数据' in h)"
#   期望：h2: 11 / kw: True

# 2) 锚点完整
curl -s https://workbench.haocoming.top/privacy | grep -o 'id="[a-z]*"' | sort -u
#   期望包含上面 11 个 id（外加 toc 等容器）

# 3) 浏览器禁用 JavaScript 打开 /privacy：能看到完整正文、目录可点击
# 4) 移动端 390 宽与桌面 1440 宽视觉不变（目录、高亮块、卡片）
```

> ⚠️ 注意：不要用 `curl … | grep -c '<h2'` 当验收判据——现在脚本字符串里也含 `<h2`，会误判为已有 11 个。必须先剔除 `<script>` 段。

## 回归验证（改完一次性跑）

```bash
# 页面
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" https://workbench.haocoming.top/privacy        # 200 text/html
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" https://workbench.haocoming.top/privacy.json   # 200 application/json
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" https://workbench.haocoming.top/privacy.md     # 200 text/markdown

# 缓存与协商
curl -s -o /dev/null -w "%{http_code}\n" -H 'If-None-Match: <etag>' https://workbench.haocoming.top/privacy.json   # 304
curl -s -o /dev/null -w "%{http_code}\n" -X OPTIONS https://workbench.haocoming.top/privacy.json                    # 204

# 后台仍可用：GET /api/privacy-policy-document（带 X-Auth-Token）→ 200；不带 → 401
# 未发布时：published=false → /privacy、/privacy.json、/privacy.md 全部 404
```

回滚：现有静态页仍保留在 `/opt/wh-site/privacy-page/privacy.html`，nginx 切回 `root … try_files` 即可 10 秒恢复，本次两项修复都不改数据目录，回滚无数据风险。

## 对客户端的影响

- 阶段 1（已接入）只依赖 `/privacy.json` 的 `version` 与 `public_url`，**本次修复不影响客户端**，无需客户端跟版。
- 阶段 2（客户端内嵌渲染）取决于 `body_html` 是否补齐；不补也可以，客户端用 `marked` + `dompurify` 渲染 `body_markdown`，只是需要服务端确认「长期只提供 markdown」。
