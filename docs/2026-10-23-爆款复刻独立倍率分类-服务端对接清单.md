# 爆款复刻 · 独立倍率分类对接清单

> 状态：**客户端已就绪，等服务器新增 `pod_replica` 分类**
> 日期：2026-10-23
> 面向：远端计费服务维护者（`workbench.haocoming.top/auth-api`）
> 前置：`GET /api/customer/billing/summary` 的 `pricing.pod_modules` 已上线（全定制 / 半定制 / 裂变三条）

---

## 1. 背景与结论

爆款复刻（普通生成）当前与 POD 全定制**同价同倍率**：`_multiplier_category()` 走 `startswith("pod")` 兜底，归入 `pod` 分类。运营希望复刻能**单独调价**，因此拆出一个独立倍率分类。

明确不做的部分：

- **不开独立冻结/结算通道**。复刻与全定制报文完全同构（按款、`scope=["title","four_grid"]`），单独开 `/pod-replica/*` 只会增加双端幂等/重试/对账的维护成本。
- **不改 `billing_profile`**。复刻继续上报 `pod_replica_v1_a`，流水归类不变。
- **不新增版本字段**。继续复用 `pricing.rule_version` / `effective_at`。

## 2. 客户端已定的契约（服务端按此实现）

### 2.1 命名

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 倍率分类 id | `pod_replica` | 写进 `billing_multiplier_rules.category`、`multipliers` 的 key、管理端卡片 id |
| `pod_modules` 条目 key | `pod_replica_v1_a` | 与现有 `billing_profile` 一致；高清直出开放后用 `pod_replica_v1_b` |
| `unit_label` | `款` | 客户端原样展示，不做换算 |

### 2.2 新增条目示例（当前 90% 倍率）

```json
{
  "key": "pod_replica_v1_a",
  "label": "POD 爆款复刻",
  "unit_label": "款",
  "charge_min_points": 40.5,
  "charge_max_points": 45,
  "base_charge_min_points": 45,
  "base_charge_max_points": 50,
  "multiplier_percent": 90
}
```

### 2.3 客户端读取规则

- **只读 `pricing.pod_modules`**，不读 `multipliers`，不需要客户端再换算。
- `label` 服务端优先；缺失时客户端兜底：`pod_replica_v1_a → POD 爆款复刻`、`pod_replica_v1_b → POD 爆款复刻 · 高清直出`。
- 数组顺序 = 面板展示顺序，建议 `pod_random_v1 → pod_semi_v1 → pod_fission_v1 → pod_replica_v1_a`。
- `charge_*` 必须是**已乘倍率的最终价**；`base_charge_*` 用于展示「基准 … · 当前倍率 …」副行。
- **小数最多 1 位**（四舍五入），与现有 `40.5` 口径一致，不要输出 `39.15`。
- 数组缺失/为空 → 客户端整块隐藏；单条缺 `charge_min_points`/`charge_max_points` → 仅过滤该条，不报错。

## 3. 服务端改造清单

### 3.1 数据库

1. `billing_multiplier_rules.category` 增加 `pod_replica`。
   SQLite 带 CHECK 约束需重建表（与新增 `pod_semi` / `pod_fission` 时同一做法）。
2. `billing_multiplier_changelog.category` 若有 CHECK，一并放开。
3. 初始行：`points_per_unit = NULL`、`multiplier_percent = 100`（恢复基础定价语义，与其余分类一致）。

### 3.2 分类映射（顺序是重点）

`_multiplier_category()` 中 **replica 判断必须放在 `startswith("pod")` 兜底之前**，否则复刻仍会被归到 `pod`，拆分无效：

```python
def _multiplier_category(profile: str) -> str:
    key = str(profile or "")
    if key in {"pod_replica_v1", "pod_replica_v1_a", "pod_replica_v1_b"}:
        return "pod_replica"
    if key == "pod_semi_v1":
        return "pod_semi"
    if key == "pod_fission_v1":
        return "pod_fission"
    return "pod" if key.startswith("pod") else "ai"
```

同时把 `pod_replica` 加进 `MULTIPLIER_CATEGORIES`，否则 `_load_multipliers()` 不会产出该分类。

> 历史冻结记录里可能出现无后缀的 `pod_replica_v1`，映射里一并归到 `pod_replica`，保证重试/续跑口径一致。

### 3.3 定价生成

- 基准与全定制一致：`base_range_points = [45, 50]`，`base_points_per_unit = 45`。
- 生效价 = 基准 × `multiplier_percent`；管理员设了 `points_per_unit` 则按固定价。
- 在 `active_pricing()` 里追加复刻条目，**不要**另写一份 summary 逻辑——summary 与 rules 必须天然同口径。
- `multipliers.pod_replica` 建议保持四个分类结构一致：`multiplier_percent` / `points_per_unit` / `base_points_per_unit` / `effective_points_per_unit` / `base_range_points` / `dynamic_range_points`。

### 3.4 管理端

- 价格倍率页新增第 5 张卡「POD 爆款复刻」：当前单条价值、基准、派生倍率、更新时间/操作人/原因、80%~120% 快捷按钮、单条价值输入、「应用」「恢复基础定价」。
- 变更记录表 category 展示名补 `pod_replica → POD 爆款复刻`。
- 页面提示保持现有口径：调价只影响之后新冻结的任务，已冻结按快照结算。

### 3.5 不需要动

| 项 | 说明 |
| --- | --- |
| `/batch/freeze`、`/batch/settle` 白名单 | 复刻已走通用通道，不新增 |
| `billing_profile` 取值 | 继续 `pod_replica_v1_a`，流水归类不变 |
| 消费流水 / `usage_history()` | 客户端已按画像显示「POD 爆款复刻」 |
| 在途任务结算 | 按冻结快照，不受新分类影响 |
| 老客户端 | 不识 `pod_modules`，不渲染该区块，行为不变 |

## 4. 自测与验收

1. `GET /api/customer/billing/summary` → `pod_modules` 4 条，复刻 `40.5 ~ 45`，其余三条数值不变。
2. 管理端把复刻调到 80% → 复刻变 `36 ~ 40`，全定制仍 `40.5 ~ 45`（互不影响）。
3. 调价前冻结、调价后结算 → 按冻结快照金额，不出现补扣/多退。
4. `GET /api/customer/billing/rules` → `multipliers.pod_replica` 与 summary 的复刻条目数值一致。
5. 造一个不带复刻条目的旧响应做回归 → 客户端不报错，只是少一张卡。
6. 用历史 `pod_replica_v1`（无后缀）的冻结记录做一次续跑 → 归类仍为复刻，金额不串到全定制。

## 5. 上线顺序

1. 服务端迁移 + 分类映射 + `pod_modules` 追加 → 重启 `wh-customer-auth` → 主动失效 `pricing:active` / 倍率缓存。
2. 管理端价格倍率页发布第 5 张卡。
3. 客户端**无需发版**：用户点「个人中心 → 计费规则 → 刷新」即可看到第 4 张卡（余额概要有 30 秒本地缓存，最迟自动刷新后出现）。

> 若之后开放高清直出（B 档，`pod_replica_v1_b`，一次上报扣 4 倍），只需在 `pod_modules` 再追加一条 `unit_label: "款"` 的条目（价格 = A 档 ×4），客户端同样零改动。
