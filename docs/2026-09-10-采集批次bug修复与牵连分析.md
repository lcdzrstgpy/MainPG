日期：2026-09-10　范围：`product_processing` 草稿池「采集批次」闭环
分支：`bigdogbujiao`（工作区已有未提交改动，本次改动与其叠加，未冲突）

## 一、结论速览

| # | Bug | 严重度 | 状态 |
|---|---|---|---|
| 1 | 24h 自动清理（`purge_expired_draft_batches`）**从未落库**，功能形同虚设 | 高 | 已修 |
| 2 | 自动清理会把**已提交处理**的草稿一起软删，破坏任务预检/最终表格导出的数据源 | 高（被 #1 掩盖） | 已修 |

一句话根因：**写操作跑在只读会话里 + 批次口径混用了「池内待处理」与「全部非删除」。**

## 二、Bug 1：自动清理是空操作（根因证据）

`repository.purge_expired_draft_batches` 用 `with self.database.sessions() as session:` 做写操作。
`sessionmaker` 产出的 `Session` 作为上下文管理器时 `__exit__` 只调用 `close()`（SQLAlchemy 2.0.52 `orm/session.py:1813`），**不会 commit**，关闭即回滚。全仓扫描确认：`repository.py` 中只有这一处 `sessions()` 里带写操作，其余写路径（`delete_drafts` / `restore_drafts` / `mark_drafts_status` / `delete_draft_batch`）都用 `sessions.begin()`。

实测（`outputs/probe_batch_purge.py`，修复前）：

```
before purge: [('batch-new', 'draft'), ('batch-old', 'draft')]
purge returned removed = 1          ← 返回值骗人
after purge:  [('batch-new', 'draft'), ('batch-old', 'draft')]
RESULT: ROLLED-BACK (purge is a no-op)
```

→ 「超过 24 小时的批次自动清理」文案从未生效，批次面板无限堆积历史批次。

**修复**：改用 `sessions.begin()`（写事务提交）。

## 三、Bug 2：清理会误伤已提交处理的草稿（牵连关键）

原过滤条件是 `status != 'deleted'`，会把 `processing` / `processed` 的草稿一并软删。而这两类草稿行是下游的**数据源**：

- `service.py:4114` `export_final_workbook`：读草稿的 `preview_overrides` 覆盖任务快照 —— 草稿没了就静默回退到处理时快照，**用户在预检页保存的标题/描述/图片修改会从导出表格里消失**；
- `service.py:3355` `task_preview`：读草稿的 `preview_overrides` / `preview_revision` / `media_contract_version`，草稿没了会退化到 `media_contract_version=1`，**v2 媒体合同的预检图列表可能错位**；
- `repository.py:468` 采集重复命中时对 `processing/processed` 有跳过逻辑，依赖这些行仍然可读。

**修复**：清理目标限定 `status == 'draft'`（草稿池内待处理的候选）；批次过期判定也按池内草稿的最早创建时间。已提交处理的草稿不再被自动清理。

## 四、Bug 3：批次删除同样误伤

`delete_draft_batch` 原 `status != 'deleted'`。配合 Bug 2 的口径，**用户在批次面板「全选批次 → 删除」时会把混合批次里已处理的草稿一起软删**，导出随即丢人工覆盖。

**修复**：同样限定 `status == 'draft'`，与「批次面板只列池内候选」自洽。副作用：删除后的提示条数（`已删除 N 个批次、共 M 条草稿`）与面板显示条数从此完全一致（修复前 M 会虚高）。

## 五、Bug 4：切换批次后勾选残留（前端）

`ProductProcessingVerifyPage.tsx` 中，切换 `activeBatchId` 只触发 `refresh()` 重拉列表，**不清空也不收敛 `selectedIds`**。于是：

- 顶栏「已勾选 N」计数虚高（数字对不上可见列表）；
- `handleProcess` 用 `Array.from(selectedIds)` 提交（`service.py` 侧不校验可见性），**把上一个批次的、当前完全不可见的草稿一起送进 AI 处理**。

**修复**：`refresh()` 拉到新列表后，把 `selectedIds` / `premiumIds` 收敛到本次加载结果里存在的草稿（集合未变化时返回原引用，避免多余渲染）。覆盖场景：切换批次、批次被 24h 清理、外部已提交处理。

## 六、连带影响排查（本次改动的 blast radius）

| 牵连点 | 是否受影响 | 说明 |
|---|---|---|
| 最终表格导出 `export_final_workbook` | **受保护** | 已处理草稿不再被清理/删除，`preview_overrides` 仍可读 |
| 任务预检 `task_preview` | **受保护** | `media_contract_version` / `preview_revision` 仍可读 |
| 草稿池列表 `/drafts` | 无变化 | 默认本来就是 `status == 'draft'`，本次只是让批次口径与它对齐 |
| 上架 / POD / 尺寸画布等下游 | 无变化 | 只读 task 侧结果与产物文件，不依赖草稿批次 |
| 采集侧（整店/插件/每日选品） | 无变化 | 写入 `selection_run_id` 的逻辑未动；重复采集命中已删草稿仍会复用并复活该行（`repository.py:471-481`） |
| 批次接口调用方 | 仅 1 处 | 全仓仅 `ProductProcessingVerifyPage.tsx` 调用 `/draft-batches`，无其他消费者 |
| 前端行为变化 | 有 | 批次草稿全部提交处理后，该批次从面板消失、`activeBatchId` 自动回落到「全部草稿」 |

## 八、未修但需知（不建议本次动）

1. **批次面板上限 50**：前端不传 `limit`，路由默认 `limit=50, le=200`，且忽略 `has_more`。待处理批次超过 50 个时旧批次不可见。（本修后概率很低）
2. **搜索/筛选与勾选的错位**：搜索词过滤只影响展示，不影响 `selectedIds`，清空搜索后提交仍会带上被过滤掉的勾选。建议后续在做「提交前复核」入口时一并处理。
3. **批次删除无二次确认**：`删除选中批次` 是破坏性操作，仅靠软删 + 无撤销入口兜底。
