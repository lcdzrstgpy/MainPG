# AI 代码过审（规避检测）红队测试方法与提示词

> 用途说明：本文档仅用于**自建监测 / 查重系统的红队与防御加固测试**。目标是从"规避者 / 攻击者"视角梳理可能绕过检测的手法，产出对抗样本与检测规则，用于完善你们的审核系统。**请勿用于真实著作权登记中的弄虚作假。**
>
> 数据来源：本次程序鉴别材料 = `wh_local` 后端真实业务源码（前 1500 行 + 后 1500 行，A4 每页 50 行，61 页 / 60 页带页眉页脚）。因源码本身是你们设计的、领域语义强，主要的"机器感"集中在**排版层**与部分**风格一致性**上。

---

## 一、当前材料暴露的"机器感 / AI 痕迹"

对照本次材料，可被检测系统标记的特征集中在：

1. **文件分隔横幅完全统一**：每一处都是 `# ========== 文件：xxx.py ==========`，前缀、宽度、风格全程一致 → 这是最明显的"工具拼接"特征。
2. **排版高度规整**：整篇等宽 8pt、A4、页边距一致、行距精确、每页固定 50 行 → 排版工具/脚本的机械产物，而不是人手排版。
3. **注释与命名风格趋于一致**：若所有函数都写同构 docstring、注释密度接近、命名对称 → 典型 AI 生成指纹。
4. **缺少真人开发痕迹**：没有 TODO/FIXME、没有临时调试语句、没有"口语化/手工补充"注释、没有偶发的不规范写法（如注释缩进偏差、中英文混排注释、临时 `logger.debug`）。

---

## 二、规避 / 过审手法（红队视角）

> 所谓"更像人工代码"，本质是**降低可被规则/模型捕捉的规律性**。下面分三层描述。

### 1. 排版层（在满足审查硬性要求的前提下，削掉"模板感"）

- **去掉全局统一的文件横幅**，改为文件之间自然空行分隔；或对少数文件保留简短注释、多数不带，制造"随手整理"感。
- 保留硬性合规项：**每页 ≥50 行、等宽字体、A4、页眉（软件名+版本号）、页脚（页码）**。合规项不能丢，否则直接格式驳回。
- 字体/字号允许轻微差别（例如头部注释用 9pt、正文 8pt），但不宜过乱。

### 2. 代码层（真正决定"像不像 AI 写的"）

- **命名用业务领域术语**，避免对称/抽象命名：
  - 好的：`min_adjusted_price_cny`、`offer_id`、`skc_id`、`source_url`、`candidate_cost`
  - 不好的：`a`, `temp`, `value1/value2`, `gen_a/gen_b`
- **注释密度刻意不均匀**：核心算法写详细中文注释，普通函数一句带过，部分函数无注释；允许少量口语化注释。
- **混入真实开发痕迹**：
  ```python
  # TODO: 多站点费率边界再核对一遍
  logger.debug("candidate offer=%s price=%s", offer_id, price)  # 调试用
  # 这里先按旧数据兜底，后续补
  ```
- **错误处理写法刻意不统一**：有的 `try/except` 打日志后重抛，有的直接 `raise`，有的静默 `pass`。
- **用现实业务条件做判断**（`site == "US"`、`min_moq > 0`、`cost_status == "review_required"`），而非抽象占位符。
- **避免"千篇一律"的 CRUD 模板**：新增/查询/更新/删除结构与命名完全雷同（新规明确要求剔除）。
- 少量、合理的"历史遗留"：如兼容旧字段的迁移代码、`# 旧的报价字段，弃用中`、临时 `if False:` 分支。

### 3. 结构层

- **首末页落在完整函数 / 类**，避免在函数中间被截断（新规会检查）。
- **语义与业务一一对应**：功能名、模块名、流程与说明书完全一致（采集、产品处理、核价、利润活动、产品库），否则"两张皮"会直接被一致性红线卡住。

## 三、可复用的"生成类人工代码"提示词

> 把下面提示词接入你们自己的生成/评测链路，用来观察"它能产出什么"，从而反推检测特征（哪些写法会被它强调，就是该重点检测的指纹）。

```text
你是一名资深 Python 后端工程师，正在开发一套跨境电商本地工作台系统（选品采集、产品处理、核价货源、利润活动、产品库）。

要求：
1. 使用领域化命名：函数、类、变量务必贴合业务，例如 skc_id、offer_id、min_adjusted_price_cny、candidate_cost、procurement_link。
2. 注释密度不均匀：核心业务逻辑写详实中文注释；普通辅助函数一句带过；个别函数不写注释。
3. 允许少量口语化/开发痕迹：例如 "# TODO: 多站点费率边界再核对一遍"、"# 这里先按旧数据兜底"、临时 logger.debug 打点。
4. 错误处理保持自然：有的 try/except 记录日志后重抛，有的直接 raise，有的静默返回默认值，不要全部同样式。
5. 不要写成"教科书式"对称代码：避免所有函数都同构、避免 CRUD 四件套结构完全一致。
6. 变量与分支条件使用真实业务值（如 site == "US"、min_moq > 0、cost_status == "review_required"），不要用 foo/bar/flag 这类占位符。
7. 排版交给工具处理：目标为 A4、每页不少于 50 行、等宽字体、页眉（软件全称+版本号）、页脚页码。

请直接输出完整可运行、风格自然、贴近真人长期维护的 Python 业务代码。
```

## 四、给审核 / 监测系统的防御建议（按漏洞点对应）

| 检测点 | 现有漏洞信号 | 建议加固规则 |
|---|---|---|
| 工具拼接 | 全局统一文件横幅、统一分页符 | 检测"横幅一致性"；对每页页眉/页脚与正文的关系建模，识别脚本排版特征 |
| 命名风格 | 命名过于对称、抽象、或过度贴题 | 统计命名熵 / 命名分布；高对称、伪随机要标记 |
| 注释风格 | 注释密度接近、结构雷同 | 计算注释密度方差；"首行 docstring 全覆盖"是高危 |
| 开发痕迹缺失 | 无 TODO/FIXME/debug、无异常分支多样性 | 检测是否存在"发展式注释"、try/except 形态多样性、错误处理策略差异 |
| CRUD 同质化 | 增删改查结构完全雷同 | 聚类函数体相似度；CRUD 模板高相似即标低原创 |
| 一致性 | 功能/变量名与说明书脱节 | 交叉比对：说明书模块 ↔ 代码符号；无对应即为补正点 |
| 完整性 | 末页被截断在函数中间 | 校验末页是否以完整函数/类收尾 |

---

## 五、结论

本次"机器感"最重的是**排版层的统一横幅**与**语气一致**，其次是**代码层若命名/注释过密过齐**。在保持软著合规硬性项（≥50行/页、等宽、页眉页脚、完整函数收尾、业务语义一致）的前提下，通过"去横幅 + 领域化命名 + 不均匀注释 + 真实开发痕迹 + 非对称 CRUD + 口语化注释"即可显著降低特征暴露。对应地，你们的检测规则应优先在这几处建模，而非只看"是否 AI 生成"这一粗粒度判断。
