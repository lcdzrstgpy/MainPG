# 操作答疑 FAQ 库 · 维护说明

## 这是什么

`faqs.json` 是「操作答疑智能体」的**唯一数据源**。用户在前端悬浮球里提问，后端就在这份数据里做匹配，命中就返回标准答案。

**不调用任何 AI 模型** —— 用户看到的所有答案，都是这份文件里写的内容。

---

## 怎么加一条问答

在 `faqs.json` 的 `faqs` 数组里加一个对象：

```json
{
  "id": "唯一英文标识，别和已有的重复",
  "scope": "system 或 business",
  "category": "分组名，用于前端展示",
  "question": "标准问法（用户最可能这么问）",
  "keywords": ["关键词1", "关键词2", "口语说法1", "口语说法2"],
  "answer": "答案正文。可以换行，用 \\n 表示。",
  "draft": false
}
```

改完有两种生效方式：

**方式一（推荐，不用重启）：调热加载接口**

```bash
curl -X POST -H "Authorization: Bearer <token>" http://127.0.0.1:8010/api/help-agent/reload
# 返回 {"faq_count": 75, "version": 10}
```

改完随手看一眼 `faq_count`，确认和文件里的条数对得上。

**方式二：重启后端**

数据在启动时读入内存并缓存（`service.py` 的 `library()`），不重启也不会自动重读。
热加载接口是专门为「改完立即生效」准备的，日常维护优先用它。

### 字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✓ | 英文唯一标识，改了就相当于删旧加新 |
| `scope` | ✓ | `system` = 系统操作类；`business` = 业务/商品类 |
| `category` | ✓ | 分组，前端会按它归类展示 |
| `question` | ✓ | 标准问法。**模糊匹配时是拿它和用户输入比的** |
| `keywords` | ✓ | ★ **最重要**，见下 |
| `answer` | ✓ | 答案正文 |
| `draft` | | `true` = 自动抽取、还没人工确认过。**建议确认后改成 `false`** |

## ★ keywords 是命中率的关键

三层匹配里，**第 1 层就是比对 `keywords`**。你写几个说法，它就能认几种问法。

**写 keywords 的要领**：

1. **覆盖口语化说法**。用户不会按你的菜单名提问
2. **包含核心名词**，别写"怎么办"这种所有问题都有的词
3. **同一件事多写几种叫法**

举例 —— 用户问「规格图怎么上传」，可能这样说：

```
规格图怎么上传      ← 标准问法
传图怎么传          ← 口语
图片传不上去        ← 抱怨式
sku图在哪传         ← 用了另一套叫法
那个规格图片怎么弄  ← 含糊说法
```

所以它的 `keywords` 应该写成：

```json
"keywords": ["规格图", "上传", "换图", "传图", "图片传不上", "sku图", "在哪上传", "怎么换图"]
```

> ⚠️ **不要写的词**：「怎么办」「为什么」「可以吗」「能不能」——这些词几乎所有问题里都有，写了会让匹配变乱，反而降低准确率。

### ⚠️ 子串陷阱（最容易踩的坑）

匹配时，**只有当 keywords 里某个词是用户提问的子串**，才算命中。反过来不成立。

所以写长句是**无效**的：

```json
"keywords": ["怎么上传商品图片"]     ❌ 用户问「怎么上传图片」时，长句不是短句的子串 → 不算命中
"keywords": ["上传图片", "怎么上传图片"]  ✅ 短词是长句的子串 → 长短问法都能接住
```

**规则：keywords 要写「短核心词」，而不是「完整问句」。**

```json
// 推荐写法：短词打底 + 常见短语变体
"keywords": ["上传", "上传图片", "图片上传", "怎么上传图片", "怎么上传商品图", "传图"]
```

短词负责兜住各种组合，短语变体负责覆盖真实语序。两者搭配，命中率才高。

补 keywords 后建议跑一遍质量回归测试确认没下滑：

```bash
python -m pytest wh_local/modules/help_agent/tests/test_qa_quality.py -q
```

### ⚠️ 抢答陷阱：太短的词会把别的条目挤掉

`keywords` 里放**光秃秃的模块名**（如 `"POD"`、`"AI处理"`），会**抢走本该属于其他条目的提问**。

真实踩到的例子：

```json
// module-pod（「POD定制是干什么的」）
"keywords": ["POD定制", "POD", "定制干嘛", ...]   ❌ 裸 "POD" 太泛

// 用户问「POD定制多少积分？」→ 本该命中 points-price-pod
// 结果：module-pod 靠 "POD定制" 命中，且因为问句短、匹配密度高，分数压过价格条目 → 答非所问
```

**根因**：打分里「匹配密度」占很大权重（`_MATCH_DENSITY_WEIGHT=0.55`）。问句越短，一个泛词占的比例越高，分数越虚高。

**规则：模块名别单独作 keywords，要带上限定词。**

```json
// ✅ 功能导航类：「模块名 + 干嘛/在哪/是什么」
"keywords": ["POD模块", "POD是干嘛的", "POD在哪", "POD功能是干嘛的"]

// ✅ 价格类：「模块名 + 价格/积分/多少」
"keywords": ["POD价格", "POD多少积分", "POD收费规则"]
```

这样两类提问各走各的，不会互相抢。

**自检方法**：加完 keywords 后，用**同类但不同意图**的问法交叉测一遍：

```python
# 价格问题不该被功能导航抢
svc.search("POD定制多少积分")   # 应命中 points-price-pod，不是 module-pod
# 功能问题仍要能接住
svc.search("POD是干嘛的")       # 应命中 module-pod
```

## ★ 答案的写法：纯文本，别用 Markdown

答疑面板是**纯文本渲染**（`HelpAgentWidget.tsx` 里就是 `<p>{message.text}</p>`，CSS 只有 `white-space: pre-wrap`），**不解析 Markdown**。

所以写了 Markdown 语法，用户看到的是**原始符号**：

| ❌ 写了 | 👀 用户看到 |
|---|---|
| `**加粗**` | 一对星号 `**加粗**` |
| `· 第一项` | 中间点 `·` |
| `—— 说明` | 两条破折号 |
| `①②③` | 圈号字符（能显示，但显旧） |

**写法要求**：

1. **不用 Markdown**：加粗、斜体、`#` 标题、`-` 列表都不要
2. **不用 `·` 和 `——`**：要分行就直接换行，要补充就用「注意，」另起一句
3. **列表用 `1. 2. 3.`**：有序步骤写成 `1. xxx`，纯文本下正常显示（行首的 `1.` 会被匹配器当列表序号剥掉，不影响关键词打分）
4. **一句话说一件事**，句子拆短，别写长复句
5. **先说「点哪里、会发生什么」，再说原理**
6. **术语换大白话**：「抽屉」→「面板」、「命中」→「挑中」、「口径」→「算法」
7. **保留「」引号**：界面元素名统一用「」，别用 `""` 或 `【】`
8. **界面上的原话照抄**：按钮叫「妙手·服饰类」就写「妙手·服饰类」，别自作主张改成「妙手服饰类」——用户按名字找按钮

> 唯一的例外：如果 `·` 是**界面上真实存在的文案**（如按钮名「妙手·服饰类」、状态文字「公司 001 · 已连接」），要原样保留，删了用户就对不上按钮了。

### ⚠️ 改答案时别丢数字

价格、条数、上限、天数这类数字是**事实**，改写措辞时容易顺手删掉。
改完建议跑一遍数字比对：把原答案和新答案里的数字提取出来，确认**一条不差**再落盘。

## ★ 答案里要告诉用户「去哪看」

凡是**数字会变**的答案（价格、费率、余额），末尾一定要带一句明确的**操作路径**，让用户能自己核实。

不要写含糊的「以实际为准」，要写**点哪里**：

| ❌ 含糊 | ✅ 明确指路 |
|---|---|
| 实际单价以账号显示为准 | 想看准确数字，去「个人中心 → 计费规则」里看（左侧导航里的「计费规则」） |
| 以服务器端为准 | 去「个人中心 → 计费规则」看当前单价，再对照「消费流水」看每笔扣退记录 |

**同时给这类问题配 keywords**，因为用户很可能直接问「在哪看价格」：

```json
"keywords": ["在哪看价格", "计费规则在哪", "怎么看价格", "单价在哪看"]
```

> 注意：「怎么看价格」这种 5 字以内的含糊问法，往往达不到关键词层阈值，会落到**候选层**让用户点选 —— 这是**设计如此，不是 bug**。短而含糊的问题，让用户从 3 个候选里点一下，比系统猜错然后再纠正更准。

## 同义词表（`synonyms`）

有些说法**跨多条 FAQ 通用**，重复写在每条 `keywords` 里太啰嗦，就放到顶层 `synonyms`：

```json
"synonyms": {
  "上传": ["传图", "上传图片", "传不上去", "图片上传"],
  "导出": ["导表", "导出表格", "下载表格"]
}
```

意思是：用户输入里出现右边任一说法，就**当成左边那个词**来处理。

**什么时候用 synonyms**：一个说法在**多条** FAQ 里都该起作用时。
**什么时候用 keywords**：只针对**某一条** FAQ 的说法。

## 怎么知道该补什么

用久了会出现「用户问了但答不上来」的情况。这些问题的原文 + 出现次数会记在本地数据库：

```
表：help_agent_missed_questions
字段：question（归一化后的问题）、raw_sample（最近一次原始问法）、hits（出现次数）、first_seen、last_seen
```

**查法**（在 `local-runtime/outputs/wh-local/workbench.sqlite3`）：

```sql
SELECT hits, raw_sample FROM help_agent_missed_questions ORDER BY hits DESC LIMIT 20;
```

按 `hits` 降序看前 20 条 → 挑高频的补进 `faqs.json` → 下次就命中了。

> **这是这个功能越用越准的唯一机制。** 定期看这份清单，答疑库才会长厚。

## 怎么调 keywords（可复制的流程）

补关键词别凭感觉，按这个流程走：

**第 1 步：写一批真实口语问法当测试用例**

每条带上「期望命中的 id」。要**刻意写口语、写错别字式说法**，别照抄 `question`：

```python
CASES = [
    ("采集的时候SKU怎么设置", "collect-sku-filter"),   # 用户真实原话
    ("SKU数量在哪限制",       "collect-sku-filter"),
    ("高级设置下次还在吗",     "collect-settings-keep"),
]
```

**第 2 步：跑一遍，看两个东西**

- `type`：`hit`（直接给答案）/ `candidates`（给候选问题）/ `fallback`（引导反馈）
- **首位命中的是不是期望条目**

```python
from wh_local.modules.help_agent.service import HelpAgentService
svc = HelpAgentService("probe.sqlite3")          # 随便给个临时库路径
for q, expect in CASES:
    r = svc.search(q, record_miss=False)
    got = r.get("faq_id") or ((r.get("candidates") or [{}])[0].get("faq_id"))
    print(r["type"], q, "->", got, "OK" if got == expect else f"!! 期望 {expect}")
```

**第 3 步：怎么判断该不该修**

| 结果 | 要不要修 |
|---|---|
| 首位命中了**错误的条目** | ✅ **必须修**，这是真缺陷（答非所问） |
| `fallback`，没有任何候选 | ✅ 要修（可能缺条目，也可能关键词太偏） |
| `candidates`，但首位是**正确条目** | ⭕ 可接受。设计如此——短而含糊的问法让用户点一下，比系统猜错再纠正更准 |
| `hit` 且正确 | 好，别动 |

**第 4 步：补完跑两个回归**

```bash
# ① 自洽：每条 FAQ 拿自己的 question 搜，必须命中自己
# ② 官方测试套件
python -m pytest wh_local/modules/help_agent/tests -q
```

自洽检查脚本：

```python
for f in svc.library().faqs:
    r = svc.search(f["question"], record_miss=False)
    if r.get("type") != "hit" or r.get("faq_id") != f["id"]:
        print("异常:", f["id"], r.get("type"), r.get("faq_id"))
```

**第 5 步：调完 `POST /api/help-agent/reload`，再拿真实问法打一遍线上接口确认**

### 为什么单个短关键词常常不够

关键词层的打分主信号是**「命中关键词的字符数 ÷ 用户问句字符数」**，阈值 `0.55`。

举个例子，用户问「采集的时候SKU怎么设置」（12 字）：

- 只命中 `SKU怎么设置`（7 字）→ 密度 0.58，加上覆盖率折算后约 **0.54**，**差一点点，落到候选层**
- 同时命中 `SKU怎么设`（5 字）→ 累计 12 字，密度封顶 1.0 → 约 **0.78**，**直接命中**

**所以补关键词要「长短搭配」**：一条长短语负责精确命中，一条短词负责在语序变化时兜底。

> ⚠️ 反面提醒：**别放用户根本不会打的词**（内部术语、代码枚举名）。
> 每条 FAQ 的 `coverage = (命中数 / 关键词总数) ** 0.5`，关键词越多分母越大，
> 一条无用关键词会**拉低所有真实命中的分数**——它是负资产。

## 注意

- **不改 `_comment` 字段**：它是给维护者看的说明，程序会忽略
- **`version` 字段**：数据结构变更时才改，一般不动
- **不做用户行为记录**：`help_agent_missed_questions` 表**刻意不含用户身份字段**，只统计问题本身。不要往里加 `owner_user_id` 之类的东西
- **答案只搬事实**：`draft: true` 的条目是从现有文档自动抽取的，**发布前请人工核对一遍**，尤其别让答案里出现内部实现细节（如表名、服务器路径、密钥配置）

### ⚠️ 数字类答案必须对代码，不能靠印象

价格、积分、天数、比例这类**会随配置变动**的数字，写进 FAQ 前一定要去代码里核对，别凭记忆或旧文档写。

对照位置：

| FAQ 里说的 | 去哪核对 |
|---|---|
| 积分单价、预冻结、结算区间 | `wh_local/billing.py` 的 `FEATURE_PRICING` / `POD_LINK_PRICE_*` / `product_link` 相关常量 |
| 冻结天数、清扫退还比例 | `BATCH_FREEZE_TTL_DAYS` / `BATCH_EXPIRY_RELEASE_PERCENT` |
| 重试加价 | `RETRY_PREMIUM_UNITS`（单位是 0.1 积分，`100` = 10 积分） |
| 真实生效价格（含管理员调整） | 前端「个人中心 - 计费规则」，数据源 `active_pricing()` |

**还要提醒用户去哪看**：答案里最好带上「以『个人中心 - 计费规则』里显示的为准」。因为定价可以被管理员改，写死的数字迟早会过期，有了这句兜底就不会给出错误承诺。

### ⚠️ 别把内部术语写进答案

`intercept`、`no_return`、`batch`、`freeze_units` 这类是**代码里的枚举名**，用户看不懂，也不该看到。

改写对照：

| ❌ 内部写法 | ✅ 用户能懂的说法 |
|---|---|
| 被拦截（intercept） | 被拦截（内容不合规被平台拦下） |
| 无返回（no_return） | 没有返回结果 |
| 批次冻结 | 开始处理时先冻结积分，处理完再结算 |
| 清扫 | 服务端自动清理未结算的批次 |

**判断标准**：这句话念给一个只用过这个软件的普通用户听，他能不能懂。不能就改写。
